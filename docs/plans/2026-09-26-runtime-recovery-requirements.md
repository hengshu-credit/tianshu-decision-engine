## 1. 目标

本改造同时覆盖 `rule-engine-server`、完整 Java SDK 和 HTTP-only SDK，目标是：

- 两种 SDK 与直接 HTTP 调用使用同一套服务端运行语义；
- 规则只在用户显式配置时启用幂等；
- 以根 `trace_id` 串联一次规则执行及其子规则、外数、名单、数据库、模型、实验、日志和账单；
- 异常执行可以跨请求、跨节点恢复；
- 外数、名单、数据库、模型、实验和随机步骤的已完成结果不重复产生成本；
- 规则变更后只重新执行受影响的步骤，纯计算使用最新规则重新计算；
- 恢复更新原逻辑日志，不产生重复根日志或重复逻辑模块日志；
- 节点扩容、故障接管和消息重试不改变业务结果、Trace 关联和计费事实。

## 2. 已确定的语义边界

### 2.1 标识

- 不新增 `executionId`。
- `root trace_id` 是一次逻辑规则执行从首次请求到恢复完成的主关联键。
- 子规则和模块可以拥有子 Trace，但必须保存父 Trace 关系。
- `request_id` 只表示外部请求或业务请求上下文，不自动作为幂等键。
- 幂等键只来自规则显式配置的 Operand。

### 2.2 幂等键

幂等 Operand 使用稳定的 `refType + refId` 引用，支持：

- 多字段组合；
- 非空字段拼接；
- 常量；
- 类型转换、取值和纯计算；
- 明确声明为纯函数的方法。

幂等 Operand 禁止依赖外数、数据库、名单、模型、随机数、实验路由和未声明纯函数。

值为 `null` 或空字符串的可选字段不计入键。所有字段都为空时不生成共享幂等键，默认返回 `IDEMPOTENCY_KEY_EMPTY`，避免空字符串成为全局共享键。

幂等范围至少包含：

```text
project_id + resource_type + resource_id + idempotency_key_hash
```

请求体摘要也必须保存。相同幂等键但请求摘要不同返回冲突。

### 2.3 执行模式

完整功能生产模式为 `REMOTE_FULL`：

- SDK 不下载规则和函数；
- SDK 不依赖 Redis 规则订阅；
- SDK 不在业务 JVM 中执行外数、名单、数据库、模型或实验；
- SDK 与 HTTP-only SDK 调用同一运行 API。

`LOCAL_PURE` 仅允许只依赖输入、常量和纯函数的规则，不提供跨请求断点恢复。

## 3. 步骤分类

### 3.1 不可重复步骤

必须持久化结果和依赖摘要：

- 外数调用；
- 名单匹配；
- 数据库查询；
- 模型执行；
- 分流实验选组；
- 随机数；
- 依赖上述来源的衍生变量；
- 非纯函数；
- 已产生外部副作用的动作。

### 3.2 可重复纯计算

允许在恢复时按最新规则重新计算：

- 算术和字符串运算；
- 条件判断；
- 纯变量赋值；
- 标记为纯的函数；
- 不依赖外部来源的子规则。

### 3.3 稳定步骤 ID

步骤 ID 必须基于规则节点、字段 ID、子规则 ID、数据源 ID、模型 ID、实验组 ID 等稳定身份，不能使用脚本行号、临时数组下标或显示名称。

## 5. 恢复规则

### 5.1 第一次执行

```text
计算幂等键
→ 创建执行状态
→ 生成根 trace_id
→ 执行规则
→ 每个不可重复步骤完成后写检查点
→ 发生异常时保存当前状态
```

### 5.2 业务重试

```text
读取同一幂等键执行状态
→ 校验完整输入摘要
→ 加载当前已发布规则
→ 按步骤比较依赖摘要
→ 复用未变化的不可重复结果
→ 重新计算纯逻辑
→ 重新执行受配置影响的步骤
→ 完成剩余步骤
```

### 5.3 配置变化

外数、名单、数据库、模型、实验、随机数、函数和衍生变量分别计算配置摘要。

- 配置摘要未变化：复用成功检查点；
- 配置摘要变化：该步骤重新执行；
- 受影响的下游步骤重新执行或重新计算；
- 不受影响的已完成步骤继续复用；
- 纯计算规则修改可以继续恢复；
- 已完成不可重复步骤的输入或资源配置变化，且无法安全映射时返回 `RESUME_BLOCKED`；
- 实验配置或随机配置变化时重新路由/重新生成；未变化时保留旧结果。

不能只比较整条规则的 revision，必须比较步骤输入摘要、依赖摘要和资源版本摘要。

## 6. 外数未知状态

外数请求已发出但节点未收到响应时，状态为 `UNKNOWN_RETRYABLE`，允许业务重试。

- 使用同一个根 Trace 和逻辑模块 Trace；
- 增加 `attempt_no`；
- 保存每次实际供应商请求号；
- 新响应覆盖当前逻辑结果；
- 晚到的旧响应只能追加到尝试历史，不能覆盖已经确定的新结果；
- 供应商支持幂等键时复用供应商键；
- 供应商不支持时允许重试，但标记 `possible_duplicate=true`。

## 7. 日志和账单

### 7.1 根日志

`rule_execution_log` 以 `root_trace_id` 定位逻辑执行。恢复时更新原行，不新增恢复根日志。

### 7.2 模块日志

外数、名单、数据库和模型使用：

```text
root_trace_id + module_trace_id + step_id
```

作为逻辑调用身份。每个逻辑调用保留一条当前记录，所有物理尝试存入 `attempt_history`，确保恢复不产生重复逻辑日志，同时完整保留所有调用尝试。

### 7.3 账单

账单按根 Trace、计费目标、计费项和资源做幂等更新。已复用结果不重复计费；配置变化后实际重新发生的调用按计费策略记录。

当前账单表缺少根 Trace，运行时数据库/名单/模型日志也没有完整填充根 Trace，需要补齐。

## 8. 多节点和基础设施

- MySQL 保存执行状态和检查点；
- Redis 保存恢复租约、fencing token 和短期并发状态；
- 节点本地缓存只用于性能，不承担正确性；
- 同一幂等键同时只有一个恢复者；
- Redis Pub/Sub 保留作低延迟通知，但发布事实必须可重放；
- outbox 使用租约或 `FOR UPDATE SKIP LOCKED`；
- 项目级 QPS、外数 QPS 和并发限制使用共享限流；
- 控制台 Session 使用共享 Session 或会话保持；
- 结构迁移由独立迁移任务执行，不由每个运行副本启动时执行；
- 关键日志和计费不能使用当前“队列满即丢弃”的策略；
- 规则执行、日志写入、控制面使用隔离连接池。

## 9. SDK/HTTP 统一协议

统一运行请求至少包含：

```text
resource
params
clientAppName
traceEnabled
```

统一响应至少包含：

```text
traceId
status
result
error
resumed
attemptNo
reusedCount
reexecutedCount
revisionId
artifactDigest
```

状态需要区分：

```text
SUCCESS
FAILED
UNKNOWN
IN_PROGRESS
CONFLICT
RESUME_BLOCKED
RATE_LIMITED
TIMEOUT
```

网络超时不能直接降级为普通业务失败，也不能自动重复执行未知副作用请求。应提供状态查询或恢复入口。

实验需要新增项目鉴权的运行入口；不能复用当前管理端实验执行接口。独立模型调用如果对外开放，也需要项目鉴权的运行入口；管理端模型测试接口不能直接作为业务接口。

## 11. 本次已落地内容
