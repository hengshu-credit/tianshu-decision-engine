# 天枢决策引擎功能优化需求与计划表

版本日期为 2026-11-11。需求来自[本次产品与实现核查](../research/2026-11-11-product-review.md)。业务人员需要用已有内容配成规则，审批者需要确认批准的是哪一版，接入团队需要解释一次执行的结果和成本。

2026-11-12 已修复最近执行定位、测试结构审计及规则配置后各环节的重复工作。分段耗时见[设计器操作对照记录](../research/2026-11-12-rule-designer-latency.md)。

## 配置需求

**选择已知内容。** 页面知道字段、函数、名单、模型或 API 时，允许按业务名称或原始编码选择，展示类型、所属资源和适用版本。平台资源保存 ID 和引用类型。已知子字段保存自身身份，固定版本携带所属资源及版本身份。动态数据的属性保留来源和相对路径。用户输入的大小写、特殊字符和数字精度须可往返。

**组合条件与动作。** 配置人员可以逐项选择左值、比较方式、右值、命中动作、写入目标和结果。对可表达的运算、函数调用、名单匹配和赋值，常规任务的手写 QL 次数目标为零。直接 SQL、已有 QL 脚本和手工协议路径继续支持编辑；样例缺少结构时说明如何补充样例或手工指定。

**确认效果。** 保存前看到的是当前编辑内容，测试前看到的是所选来源，测试后看到的是实际执行身份。执行成功、通过业务断言、具备发布证据分别显示。选了会实际写名单或访问计费来源的规则，应能在提交前核对可静态识别的影响。

**推进与追溯。** 从项目工作台进入配置带入当前项目；从某次执行开始排查时带入该次执行身份。操作按钮、推荐项、列表数据和服务端授权使用同一范围。审批、离线迁移、版本覆盖后仍能查到原修订与配置依据。

## 排期

P0 表示会误认执行版本、遗漏真实操作记录或产生错误业务判断。P1 表示已知配置要求重复录入、易错或无法直接定位。P2 表示先验证规模或可用性假设。阶段给出先后和前置条件；人日是开发、测试合计的初估，任务有明确收益后再占用排期。

| --- | --- | --- | --- | --- |

## 跨模块验收任务

下一批先用真实 SQL 样例评估列选择，再用原始报文、处理中间副本及文件命名样例验证外数和 SFTP。工作台和复杂矩阵的规模测量可独立进行。每批以同一任务的配置步骤、错误和执行结果作前后对照；已有入口能顺畅完成的场景沿用现状。

| 交给使用者的任务 | 必须记录什么 | 何时可以修改流程 |
| --- | --- | --- |
| 首次建项目，配置“评分达到阈值则复核”，保存一个命中和一个边界用例，交给另一人审批 | 多少次输入协议路径、多少段手写 QL、是否选错同名字段、第一次成功完成的位置 | 已声明字段仍需手输、必须编写同等可视化可表达的脚本，或错误只在发布后暴露 |
| 用供应商样例、带别名 SQL、对象数组、SFTP 模板分别提供同一个业务指标 | 候选来自哪份结构，选择时和实际取值时的类型；保留零值、空值、点号键；加载失败能否重试 | 对现有可识别字段，选择能减少输入，且与运行时读取结果一致。协议键、目录和平台资源三类身份分别验收 |
| 在草稿、冻结版本、业务版本和当前生产之间切换，让同一规则输出两个不同值 | 输入、影响清单、测试结果、回归报告及日志的修订 ID；覆盖发布发生在打开页面之后的表现 | 有一处使用了别的版本、错误显示通过或允许提前发起真实调用，即作为缺陷修复 |
| 模型输出经函数参与规则，规则加入分流实验；从一次失败找到原因并核对账单 | 能否查到规则版本、实验组、模型、外数重试与费用归属；记录需要手动重输的筛选条件 | 归因错误、现成 trace 丢失，或同一信息在多个页面必须重复录入 |
| 导入一份含同名字段、固定模型版本、名单及函数依赖的迁移包；重试一次 | 绑定表、差异、审批状态、执行输出。核对原库与目标库的 ID 不同仍能正确绑定 | 出现误绑定、重复创建、重试使用旧范围或无法指出待处理依赖 |
| 从空库首次登录，再分别以只读、配置、审批三个身份工作；演练发布包恢复 | 按项目核对可用动作、操作记录和授权撤销；记录恢复版本、逐表行数和内容校验 | 按真实操作证明授权、追溯或恢复链路存在问题。页面调整以能修复具体问题为前提 |

## 取舍与验收口径

- 保留一级菜单平铺。项目首页已有工作台，九种模型已有用途说明，模型、外数和数据库已有测试入口。后续优先让现有入口能完成具体任务。
- 业务编码和协议字段原样保存。对平台资源按稳定 ID、引用类型和版本绑定；对外部结构按所选样例生成精确路径。已有合法手工配置可以继续编辑。
- 已声明字段的标准任务以 **0 次手输路径、0 段手写 QL、保存重开结果一致** 为验收目标。没有样例的外部协议或专门的脚本开发任务单列统计。真实业务人员的完成率需要现场采样。
- 任何改动先记录原步骤及错误，再记录同一任务在新版本的步骤、请求数和执行结果。若收益只来源于熟悉度、配色偏好或未经验证的推测，保留原流程，继续观察。
- 性能改动先明确瓶颈和业务预算。容量报告记录数据规模、版本、设备、缓存状态、并发与外部延迟，分别出服务端、runtime/SDK 和外部来源结果；单机模拟基准只用于其测试场景。
