# 天枢决策引擎功能优化与完善需求（重新梳理版）

建立日期：2026-10-08；最近迭代：2026-10-11。依据：[本次代码与产品复核](../research/tianshu-review-2026-10-08.md)。本表独立于已有规划；不包含隐私脱敏事项，不将已落地功能重新列成待开发。

## 产品目标和边界

追加验收约束：前端选定的变量、对象、规则、模型、分流、外数、函数及方法版本必须与实际执行身份一致；版本号、稳定绑定ID、不可变快照ID和修订ID分别处理。跟随生效配置与固定历史快照需要明确标识，不能选定版本失败后静默执行当前内容。

业务配置者能够完成“准备资源 → 配置规则 → 用真实输入验证 → 送审 → 发布 → 追溯结果”，每一步知道当前状态、阻塞原因和下一步。技术接入与运维人员能够基于明确容量与故障指标部署，不靠无限扩大队列掩盖瓶颈。

保留一级菜单平铺、直接 SQL、自填名称/编码原样保存、所有引用通过 ID、输出引用显式 ref_type。筛选与操作共用响应式工具栏。新功能复用现有 Schema、预检、审批、版本和追踪体系。

新增业务配置约束：规则配置与验证尽可能少要求手写QL。常见比较、区间、集合、组合条件和动作采用结构化表单与可视化交互；测试优先通过输入样例、预期结果和明确字段校验完成。只有结构化能力确实无法覆盖的场景才需要可选表达式；已保存的用户脚本继续兼容。

## 关键需求展开

### 新增、依赖与恢复的统一约定（2026-10-10）

保存只生成或更新草稿，不等于提交审批。新增内容未发布且没有批准记录、没有下游引用时直接删除；有下游时先处理下游。待审批的新增内容必须先由审批人驳回才能删除，不可直接删除或通过撤回绕过驳回。已发布内容的生产变更和删除继续走审批。

恢复历史内容提供“生成新版本”和“复用版本号”。二者都可以修改恢复后的内容，保存后仍是草稿；复用仅复用业务版本号，不原地修改历史快照。版本列表、对比、测试和执行归因要能区分同一业务版本号下的不同发布记录，且按稳定 ID 选择真实快照。旧编号恢复后，新编号从历史最大业务版本递增，不能从当前显示编号推算。

### N03：持久化承诺与恢复

不能简单把所有数据库写入改同步，也不能仅增加队列容量。建议首先为根执行建立最小持久化记录，至少包含事件ID、traceId、规则修订/摘要、执行状态、计费幂等键和后续扩展日志引用。只有该事实达到选定的持久化边界后才能宣称已接受。

可比较两条路线：数据库事务 outbox 与独立日志/WAL。前者复用现有数据库治理但增加请求路径写入压力；后者利于削峰但要求共享/持久化卷、磁盘配额、fsync策略、损坏检测和恢复所有权。先用实际大小与峰值压测做选择，禁止同时维护两套未经定义的一致性逻辑。

验收必须覆盖入队前后强杀、日志成功而计费失败、计费成功而确认失败、重复重放、磁盘满、数据库恢复后的追赶。成功定义为幂等结果与可审计事实，不仅是接口恢复为200。

### N05：面向业务人员的查询预算

界面继续保留SQL和参数表单。把“最多返回行数”“查询耗时上限”“结果过大处理”解释成对业务结果的影响。发布预检明确指出哪个数据库变量配置无界；不能静默截断却给出正常业务值。

运行时预算应取项目剩余时间与资源上限的较小值；JDBC秒级超时、连接池获取、驱动不响应中断等限制必须有真实驱动验收。迁移旧0配置前需要兼容策略，不在一次样式修复中突然改变结果集。

### N12—N14：配置、测试、审批共享一份事实

每次测试绑定具体草稿快照，报告明确输入样例、执行结果、测试时间及覆盖范围。配置变动使旧报告变成“已过期”，仍可查看但不得显示为当前配置已就绪。审批页指向该快照，发布校验复用现有治理能力。

新建外数的草稿测试必须使用当前草稿的地址、鉴权、请求映射、响应映射，并遵循现有调用日志与计费规则。提交前清楚告知该测试会调用供应商；mock预览和真实调用分开标注。

后端已有完整配置的 `invoke-preview` 能力，可复用执行链路；但未保存草稿不能共用 `id=0` 身份，否则可能共用连接池、并发保护和异步结果关联。需生成独立草稿试运行身份并检查所属数据源已生效，不能只删除前端禁用条件。发布测试证据还需关联修订ID/制品摘要，不能仅采信详情页内存中的上一次成功。

### N29：业务人员无需编写QL的配置与验证

常用条件通过“字段 → 比较方式 → 值”配置：区间提供两个边界，集合逐项输入，组合条件直接选择全部满足或任一满足。提示必须说明边界是否包含、缺失与null的区别，以及数字和文本是否按同一类型比较。保存时保留字段ID和精确数字文本，不根据字段名称重新绑定，不替用户改写旧脚本或旧CSV。

测试表单按输入Schema生成；“未提供”“null”“空字符串”是不同业务状态，不能统一转换为空值。未知字段、对象、数组及原始JSON可保留；超出表单能力时明确定位需要调整的字段，不能直接要求用户改写整个规则为QL。

输出预期独立于执行结果配置，业务人员选择输出字段、比较方式和固定值、区间或集合。相同规则可以有“边界内通过”“边界外拒绝”“缺少输入”等多条用例，单次和批量使用同一服务端比较规则。执行成功只表示规则正常运行；未配置预期、未能校验、配置失效和结果不符分别显示，不合并成绿色通过。配置变更后旧结果明确过期；仅在用户主动操作时采用最近结果作为JSON预期。

历史JSON快照原文保留。业务快照只比较既有执行契约中的状态、业务输出和错误，不将调试追踪深度作为业务结果复杂度；业务输出自身同名字段仍参与校验。必须继续拒绝重复字段和畸形JSON，精确数值不得先转JavaScript Number再判断相等。

验收至少覆盖：无需输入QL完成区间/集合配置、缺边界就地阻断、字段改名后仍按ID关联、正确与错误预期、未配置预期、保存重载、单次/批量一致、旧快照往返、明暗主题与窄屏。业务中文规则摘要和实际新手完成时长仍需单独验证，不能由自动化测试代替业务试用。

### N33：无需技术编码的制品导入与可信详情

业务路径为“选择制品 → 选择目标与资源绑定 → 检查并部署”。制品决定模型类型，页面展示中文名称；项目/规则应能按名称、编码检索，保存和关联仍使用真实ID。加载类型和绑定失败时明确重试，不能沿用上一个包的配置或允许空白提交；后端独立校验包类型与目标一致。

详情需要明确当前查看的修订和字段来源：草稿按指定修订的模型内容复用已有字段分析器，明确依赖当前环境资源；已发布/历史修订读取该修订制品的冻结字段、名称、类型和关联，不把来源ID交给目标实时目录重新解释。只读查看不写回管理端字段主表。切换修订时旧请求不得覆盖当前选择，损坏或缺失制品应显示错误，不伪装成0字段或回退草稿。

已发布事实、发布前校验证据和测试证据分别展示。导入批准的制品不要求用户重新补一遍“发布进度”；没有对应测试证据时写明未记录，不能因为已经发布就虚构测试通过。该视图应覆盖源目标ID碰撞、原资源改名/删除、旧版本和新草稿并存。

### N36：元数据标识从HTTP到引用关联保持精确

项目、规则、修订、制品和绑定候选的数字ID可能超过JavaScript安全整数范围。必须在原始HTTP响应进入普通数字解析之前保留其十进制文本，而不是先舍入再转字符串；相邻大ID必须保持可区分。只对明确的元数据接口与标识字段处理，业务执行结果、用户保存的modelJson字符串及普通数值维持原契约。已经失真的标识、超出服务端范围的标识及无法无损解释的非规范大数应明确报错，不能尝试猜回原ID。

### N07：容量工具使用契约

`scripts/quality-gates/run-capacity-gate.mjs` 本次将 `summary.throughput` 明确定义为成功完成决策/秒；`summary.requestRate` 是所有完成请求/秒（含失败）。以前把总量当成功吞吐的报表不得直接纵向比较。

请求文件可写 `expectedResponse`，键为以点分隔的对象字段路径，值为需要严格匹配的 JSON 标量。未提供时默认 `{"success":true}`，适配标准开放接口。自定义响应模板、管理执行端点或 runtime 必须按实际契约填写，例如：

```json
{
  "method": "POST",
  "headers": { "content-type": "application/json" },
  "body": { "params": { "age": 30 } },
  "timeoutMs": 10000,
  "expectedResponse": { "code": 200, "data.success": true, "data.result.score": 88 }
}
```

HTTP 202 不计完成成功；畸形JSON、字段缺失、类型不符也失败。点号路径不支持含点号的原始键名或JSONPath表达式。报表只记录断言字段名，复现测试时应保留受控请求定义；不把样例期望值写入公共报告。

短测通过后再做峰值阶梯与长稳测试。建议先验证300万/500万日量的10倍峰值假设，再按真实峰谷数据调整；P95/P99门限按纯计算、外数与模型场景分别制定，不用一个毫秒指标覆盖所有业务。
