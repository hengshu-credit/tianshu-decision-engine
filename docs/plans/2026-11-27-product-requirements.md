## 需求与验收

### R01 至 R04　本次交付契约

- **R01**　项目规则口径沿用工作台可见的自有规则与已关联规则，排除已删除规则。覆盖分子是至少有一份启用用例的不同规则数。空项目提示先创建，部分覆盖显示缺口，完整覆盖后提供执行入口，读取失败可重试。待补入口选取尚缺用例的最小定义 ID，进入用例页并保留项目上下文。两份用例属于同一规则、停用用例、其他项目的规则、超出 JavaScript 安全整数范围的 ID 均纳入回归。
- **R02**　从项目创建时预置项目，规则列表沿用当前范围。同一请求提交期间只能创建一次。取消编辑有保留和放弃两条路径，再次新建显示空表单。创建响应抵达后即可打开返回 ID 对应的设计器。树和流打开属性面板后，连续增加动作节点、结束节点的锚点须可点击，保存重载后执行结果一致。
- **R03**　候选搜索、根图、方向、分支及字段展开以当前起点为准。迟到的成功或失败响应不得覆盖新图。清空起点后清空画布。原位重新加载沿用当前查询。超过显示上限时保留服务端给出的原因。390 像素宽度可完成搜索、选择和出图，选框完全位于面板内。离线导出预览要区分源环境当前图、所选导出版本与包内依赖，按每一行选择的原始资源 ID 请求。
- **R04**　最近一次执行以逻辑日志视图的执行项目 ID 限定范围，按创建时间、日志 ID 倒序取一条。SQL 投影限定为流水、规则编码、版本、成功标记、耗时、调用来源及创建时间。回归同时放入同编码的其他项目、历史编码、本项目失败记录和未知归属记录，核对选中的记录及摘要值。

### R05 至 R08　业务配置

| 需求 | 问题和业务操作 | 设计与验收条件 |
| --- | --- | --- |
| R05 | 390 像素宽度下，血缘页查询区前有四块可关闭的说明，规则测试页也需经过多块说明才到规则选择。首次使用者怎样利用这些说明尚缺任务数据。 | 招募 5 名未参与该功能开发的策略人员，从给定的准入判定说明开始，只通过控制台完成项目、规则、用例和一次验证。记录在哪一步求助、误入哪个入口、首次正确结果用时。再对高频停顿点调整默认引导、字段例子或首屏排布。目标为至少 4 人独立完成，第二轮中位用时较首轮下降 25%。保留平铺导航、可关闭说明以及已选的个人偏好。 |
| R06 | 业务人员能看到供应商成功返回，却仍可能不知道变量为什么是空。API 响应分支、SQL 返回列、SFTP 文件记录、名单未命中，以及历史窗口排除记录的含义各不相同。 | 复用现有变量联测、试运行和模块调用日志，按同一输入显示所选来源、映射路径或列、实际命中结果、最后的变量值。用请求字段缺失、供应商返回空、只读查询零行、SFTP 文件未到、名单未命中和一组窗口边界数据逐项验收。历史统计额外显示范围、时间边界、是否包含本次订单与可核对的样本计数。敏感字段遵循原遮罩策略。SQL 编辑和参数绑定在原页面直接使用。 |
| R07 | 类型说明已经会解释决策表和评分卡，但业务人员仍须自己把“边界恰好相等”变成一个有预期结果的测试。 | 决策表与规则集覆盖多命中、无命中及优先级。树与流覆盖分支、终止和子规则。两种交叉表覆盖边界格、空格。两种评分卡覆盖命中贡献、初始分及等级边界。QL 覆盖稳定字段引用和异常。创建样例前展示输入与预期，用户确认后保存到对应规则并执行指定修订。人工更改预期应使回归失败并指向差异。 |
| R08 | 工作台现在能打开缺少用例的规则。字段引用检查能指出规则名称和 JSON 路径，其处理动作仍进入规则列表。多个草稿时还要重新辨别是哪一版。 | 在已有检查结果上携带可确认的定义、修订、用例及问题位置，复用设计器已有定位功能。验收改名、两个同名资源、多草稿、旧证据过期、目标修订已删除及无权限。只定位问题，编辑、执行、提交审批均由用户发起。 |

### R09 至 R12　执行、运营与部署

| 需求 | 设计要求 | 验收方法 |
| --- | --- | --- |
| R09 | 按调用方分服务端开放接口、SDK 本地执行、独立 runtime。各测冷启动、缓存命中、规则更新后第一次调用。工作负载分纯规则、8 个独立阻塞源、含依赖的串行来源、模型推理、历史派生、完整追踪。 | 在同一硬件、数据规模、并发、追踪配置下记录预热时长、样本量、成功率、吞吐、P50/P95/P99、CPU、堆与直接内存、排队和日志积压。每笔校验输出与版本。单列 30 分钟稳态和恢复期。先与业务方确定端到端预算，再将预算写入容量脚本。新增测试结果同时保留错误数和原始分布。 |
| R10 | 看一次拒绝时，应能按一条流水解释触发条件、调用来源、所用版本、缓存或重试，以及具体计费项。已有的日志、模块明细和账单各自保留自己的查询与授权。 | 使用成功、业务拒绝、超时后重试、命中缓存、实验空跑和测试调用六种样例。核对每笔根调用、子调用、尝试序号、实际费用和币种。按同一口径对账，费用为零、明细缺失、尚在写入各有清楚的解释。 |
| R11 | 对 ONNX/PMML 资产替换、函数签名变化、实验权重或版本调整，复用现有影响分析、预热、版本对比和实验日志，用固定输入展示变化。 | 对模型分别验证字段名、数据形状、样例输出与部署端能力。对函数检查引用仍使用稳定 ID、签名变化能定位调用点。对实验给定分流键和冻结版本，核对实际路由、空跑结果与正式结果。任一前置资源不可用时给出可操作的原因。 |
| R12 | 将离线迁移、线上发布和灾备恢复分别演练。迁移先做资源闭包和手工绑定预检。发布记录生效修订与 SDK 收到更新的时间。恢复同时核对数据库、二进制制品与 SFTP 文件。 | 在源、目标 ID 不同的环境验证同名资源、版本冲突、缺失绑定、中断续办和重复操作。在双实例、Redis 推送中断及 Kafka 补报场景核对执行结果、版本收敛和日志去重。按部署入口演练升级失败和恢复到独立库，核对逐表行数、内容校验、文件摘要，然后重跑一份固定业务用例。 |

### R13 与 R14　团队协作

- **R13**　为策略配置、复核审批、只读运营三类人员分别给出要完成的实际任务。在有项目覆盖和全局只读的环境中验收，记录谁能看、谁能改、谁能审批。台账中的变更可返回有权查看的记录。撤销授权后复查旧会话、历史链接、导出和待检附件。系统管理员另行演练首次初始化、账户恢复与邮件找回。
- **R14**　看板分布应可复核样本总数、有效数、排除数和时间范围。用同批数据校对按项目筛选后的数据看板、执行明细和账单汇总。配置变更另外验收品牌与字体预览、SMTP 真实送达和结果码变更后的一次外部请求。缺少数据、依赖暂不可用与账户无权查看在界面上能区分。

## 交付判定

每个阶段交付已运行的场景、实际结果和仍需环境验证的事项。策略人员负责说明预期业务结果，工程人员负责保存可复测的输入和执行口径。业务计时从用户接到任务开始，到得到并解释正确结果结束。发布验收独立核对草稿、已批准修订和线上实际使用的版本。
