# 衡枢真信授信分流、缓存与断点压测验收

三轮共 5,497 笔。授信准入、人脸活体、证照一致性、白名单分流和额度随机分流均通过正式接口执行。每笔业务结果、对端查单和执行日志均已核对。

## 环境与验证口径

两个独立 server 进程分别限制为 4 核，Java 堆上限 2,200 MiB，共用隔离的 MySQL、Redis、Elasticsearch 和模拟供应商。持续阶段开放 60 个客户端共 90 秒，结束时等待在途请求完成。突发阶段每轮同步放行 160 个请求，连续三轮。另用不同请求键进行 650 次随机分组抽样，每轮均执行一次。

MySQL 保存受理身份、租约、分组和策略修订、外数检查点、正式账单以及投递状态。ES 保存可检索的执行正文、历史特征、规则步骤和模块调用正文。对账检查 MySQL 的物理行标识及修订、解密后的 ES 正文、索引计数和待投递数量。

## 额度和随机分组

基线和加额版均在原决策流的各结束路径汇入四个子规则，计算授信分层、复核天数、跟踪评分和复核动作。加额版随后检查原额度。原额度小于等于零时拒绝且额度为零。已通过且原额度为正时增加 1,000 元。五个子规则共 16 个启用固定用例，覆盖金额 -1、0、1 以及分层、期限、评分边界。两条主流程分别通过 4 个启用固定用例。

额度实验的 2,615 笔订单中，基线 757 笔（28.95%），加额版 1858 笔（71.05%）。每笔都按独立计算的桶值核对组别。基线通过件 98 笔，额度均为 20,000 元。加额版通过件 181 笔，额度均为 21,000 元。两组的拒绝件额度均为零。白名单实验覆盖仅手机号命中、仅身份证命中、两者命中、两者均未命中的通过和拒绝路径。

## 外数和账单

三轮部分进件共享收入报告，每轮使用 7 个报告键。合计 280 次共享报告读取，首次回源 21 次，缓存命中 259 次，并发合并 0 次。每个共享键在对应轮次只回源一次。同期其他外数产生 7,126 次关闭响应缓存的调用。收入接口每笔实收均按调用 ID 和计费编码核对账单去重键。

| 专项场景 | 实际供应商调用和账单 |
|---|---|
| 双节点冷缓存，16 笔不同进件同时查询一份报告 | 回源 1 次，收入账单 1 笔，金额 0.26 元。其余 15 笔取得相同结果 |
| 已预热，同一报告跨节点、跨实验组复用 | 首次产生 0.26 元。后两笔各为 0 元。换新报告再次产生 0.26 元 |
| 同报告更换手机号，再次查询及过期后重查 | 新主体首次回源计费 0.26 元，再次命中为 0 元。旧报告键过期后重新回源计费 0.26 元 |
| 同一 trace 双节点重复受理、续跑、查单 | 专项 12 次都返回原订单和原子策略。外数调用及账单增量均为 0 |
| 对冷热缓存和断点订单再次并发重放 | 30 个 trace，原有 206 行账单和 1,798 行模块调用逐行相同 |

初次复现时，未生效的备用进件号也参与响应缓存键，16 笔相同供应商报文产生 16 笔收入费用。修复后使用生效报文、鉴权及相关响应依赖计算响应缓存键，断点仍沿用原请求的身份。Redis 二级缓存启用时，两节点可合并同键的在途读取。供应商重启使旧 OAuth 令牌失效的专项测试中，401 后沿用原幂等键刷新令牌，第二次 HTTP 返回 200，仅产生一笔收入费用。原先因 401 失败的 9 笔诊断订单也全部以原 trace 续跑成功。

## 断点与日志

单节点专项关闭另一节点后中断并重新启动执行节点，10/10 笔完成并保留原分组。双节点专项先中断 A，在 B 接管并执行时再次中断 B，再由 A 恢复，16/16 笔完成。逐笔比对实验 trace、子 trace、组、修订、制品摘要和两节点最终返回。基础身份拒绝在首次外数前结束，账单为零。

最后一轮全库对账覆盖 14,968 条执行文档、14,968 条历史特征文档、14,968 条规则步骤文档和 73,852 条调用文档，差异和待投递均为 0。前一阶段的独立回归另有 3,922 笔，1,216 份显式空人脸数组均完整保留。
