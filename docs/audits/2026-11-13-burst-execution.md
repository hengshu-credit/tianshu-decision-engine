# 服务端突发流量与断点恢复验证

2026 年 11 月 13 日，在隔离的 MySQL、Redis 和双副本服务端上验证生产分流实验。供应商使用本地 HTTP 和 SFTP 模拟服务，判定计费请求次数的依据是供应商逐单流水。应用、数据库、规则执行、模型计算、追踪、名单动作及恢复使用项目实际实现。

## 生产近似负载

两个应用副本各限制 0.45 核和 1,536 MiB，MySQL 限制 0.40 核和 1,536 MiB，Redis 0.10 核，反向代理 0.05 核。预置同项目约 60 万笔历史进件及 120 万个经纬度数值，按半天 1 万笔生成。实验根据渠道选择策略流，扩展组逐步经过名单、账务、资信、函数、异步报告、GPS 统计，最后由决策表给出额度、价格和期限。完整路径评估 50 条策略项，含 14 个同步 API、1 个返回 8,000 个字段的异步 API、10 次 DB 查询、5 次名单匹配、1 次 SFTP 读取和 3 次模型执行。提前拒绝的订单按实际路径提前结束。

以下为交付版本的结果。全程使用原执行请求格式、完整追踪和默认 90 秒同步排队上限。持续场景完成一单即补一单。混合场景按每秒 0.24 单安排背景请求，在第 40 秒另加 48 单同时到达，覆盖常规、扩展及两种提前拒绝。正确吞吐按全部已验证业务结果除以场景墙钟时间计算。P50 和 P95 包含排队及返回业务结果的时间，HTTP 202 单独计为已接收。

## 逐单核验

逐单根据请求键关联实验订单、生产组规则根追踪、MySQL 执行尝试及供应商流水。校验分组、各节点顺序、规则项、表达式追踪、DB 数值、模型调用、1 公里内当日及近 7 天、30 天数据，另按历史分批时间校验 GPS 计数。正常通过期望为额度 60,000、年利率 960 基点、期限 24 个月，拒绝时三个值归零并校验拒绝原因。

232 笔中 214 笔通过、18 笔拒绝。3122 次同步取数和 169 次付费型异步提交均与各单预期路径一致。正常异步流程每个任务进行两次结果查询。混合流量的 18 个名单任务共核对 72 条手机号、身份证明文及 MD5 记录。三个场景的执行日志队列及持久化发件箱均已排空。

## 故障演练

- 将两个应用实例的并发槽分别调成 2、同步等待容量调成 0。14 单同时提交，4 单首次就绪，10 单取得 HTTP 202 及追踪号。随后只用 GET 查询，14 单全部完成。跨副本重发同一成功订单 8 次均取得同一结果，同键更改入参返回 409，供应商未增加调用。
- 供应商已经受理异步任务、MySQL 已有任务号时，对两个应用副本同时发送 SIGKILL。11 单正在排队、8 单已经执行。重启后只读查询，85.5 秒内 19 单全部完成。恢复后整单仍只提交一次，结果查询使用原任务号。18 个拒绝动作均核对四条名单记录。
- 生产供应商已受理而结果暂未就绪时，最初返回 HTTP 202。释放模拟故障后，只用 GET 查询，后台自动沿用原任务号并取得预期定价，未发起新的供应商提交。
- 原票据暂时无结果，从两个副本同时发起 5 次恢复，一次取得执行权，其余得到进行中状态。完成原任务只增加一次结果查询，14 个已成功同步 API、10 次数据库查询、5 次名单匹配和 SFTP 读取均沿用原结果，恢复后完成剩余模型与定价。
- 供应商明确返回 HTTP 503，恢复后只重试该失败接口，取得预期定价。另一演练由供应商记录受理后主动断开响应，默认恢复没有第二次查询或业务判定，订单保留供核实。复合故障演练中，SFTP 重启后继续原单，已成功的同步接口也没有再次提交。
- 两笔已完成的无 GPS 订单曾使旧实现回退到全量历史读取。修复后，失败订单从原断点继续，没有新增供应商调用。7 天窗口的 140,756 个候选与 7,754 个命中、30 天窗口的 600,756 个候选与 30,754 个命中与逐笔口径一致。缺失坐标仍计入候选，有历史 API 字段时按稳定字段 ID 从本地回执补齐。后续负载保留这些无坐标订单。
- 显式启用 `CACHE_THEN_CALL` 后，缓存失效时重新提交，缓存命中时免去该同步供应商查询。未设置此选项的恢复保留原调用。OpenAPI 未配置幂等键的两次独立提交均取得自己的追踪号，并按映射返回正确业务结果。
- 只重启合成 SFTP 服务，保留应用实例和原连接池。重启后的第一笔业务请求成功，未配置 SFTP 读取重试。
- 成功订单按保留期清理。将测试父订单设为等待外数且已过期，父订单、已完成的子策略及两个步骤回执均保留。父子成功且全部过期后，订单状态和回执均被清理。
- 浏览器端从新建实验、选择项目及策略、添加测试组开始，验证外数开关默认关闭，手动开关、保存草稿、提交、审批和实际验证执行均完成，生产组与空跑组得到预期结果。

## 性能开销与适用范围

历史规则集统计补齐改为按已有索引的版本、主键和创建时间顺序领取，并限制每轮占用时间。原测试库预处理时约 6,400 次查询共扫描近 2 亿行。改后一次观测中的 12,360 次领取共检查 123,600 行。外数无鉴权路径跳过无用的变量目录装载，请求内复用 API 和数据源配置。MySQL 死锁记录显示，投递确认时扫描状态索引会与另一批正在更新历史小时索引的事务互相等待。改为通过二级索引读取候选，再从主键领取和确认，状态、处理时间和所有者在锁内复核。32 并发阶段的执行中采样与混合负载结束时，两次读取 MySQL 死锁计数的增量为 0。启动时也会跳过已达标日志表的字符集转换。恢复写入校验数据库租约，旧执行者无法覆盖新尝试的终态。

本次验证使用本机模拟供应商和有限时长的负载，未进行生产计费联调、数据库主从切换或数小时持续过载。后台可恢复以 MySQL 已提交订单及可读回执为前提。缺少业务键且未取得追踪号的独立重发无法可靠关联原单。供应商未返回回执且不支持按业务单号核查时，保留待核实状态，人工核实后可选择恢复方式。部署已有库前应执行 `2026-11-13-execution-queue.sql`。

本地构建及回归已覆盖全部 Maven 模块。后端共 3,060 项，默认回归 0 失败、0 错误、68 项跳过。另已启用 4 个规则统计 MySQL 集成用例并全部通过。前端 3,769 项全部通过，ESLint 通过。迁移在同一测试库连续执行两次，核对 106 张业务表和 1,519 个字段的中文注释。
