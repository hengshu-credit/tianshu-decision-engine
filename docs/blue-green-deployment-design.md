# 蓝绿部署设计：共享环境、固定入口、双版本切换

状态：**目标设计，尚未实现为可执行的蓝绿发布功能**。核查日期：2026-11-09。适用服务器：用户确认的 16 GB / 4 核或更高配置。

当前 `deploy.py` 支持目录整理、备份、停止应用、替换制品、重建及健康检查；它还没有蓝绿双槽、在线流量切换和请求排空能力。现有包运行普通更新仍会中断应用。当前可执行的维护窗口流程见 [部署说明](server-upload.md)，不能把它当成本文的在线发布流程。

## 1. 确定的架构

保留 Docker Compose，兼容现代 `docker compose` / `docker-compose`。Nginx Proxy Manager 继续管理原域名、HTTPS 和证书；不调整宿主机 Nginx、UFW、Fail2ban 或原公网端口策略。

```text
浏览器 / 业务调用方
        ↓ 原域名与端口
Nginx Proxy Manager（保持原有职责）
        ↓
常驻 Nginx 网关（前端、API，SDK 同机时也代理 SDK）
        ├── Blue：server × 2，SDK runtime × 1（可选）
        └── Green：server × 2，SDK runtime × 1（可选）
                     ↓
            同一套 MySQL / Redis / Kafka
```

平时只有一组应用承接新请求；发布时先启动另一组，验证通过后切流。旧组在请求及异步任务排空、观察期结束后停止，制品保留供回退。网关和基础设施不随普通应用发布重启。

独立 SDK 机器需要部署自己的常驻入口和两组 runtime。业务系统内嵌的 Java SDK 属于调用方应用的一部分，不能由这里的发布脚本直接更新。

## 2. 固定目录与版本目录

```text
/root/tianshu-decision-engine/
├── .env.server / .env.client          # 旧备份，不参与启动
├── config/
│   ├── .env.server                    # 生效的共享服务端配置
│   └── .env.client                    # 生效的 SDK 配置
├── docker/
│   ├── 基础设施 Compose 与数据目录     # 保留原项目名和数据
│   ├── 网关与应用 Compose 定义         # 固定定义，蓝绿能力待实现
│   └── nginx/                        # 固定配置、待发布配置及生效路由
├── deploy-prod/
│   ├── releases/<release-id>/         # 校验后的完整发布包，发布后不可修改
│   │   ├── docker/runtime/            # server.jar、runtime.jar、dist
│   │   ├── migrations/
│   │   └── BUILD-INFO.txt
│   ├── current                       # 活动版本的目录引用，拟改为原子更新的指针
│   ├── previous                      # 上一个成功版本的目录引用
│   └── history/                      # 发布、验证、迁移与回退记录
├── legacy/                           # 首次目录整理前的旧配置与源码
└── 发布 ZIP 及同名 SHA256 文件
```

当前已实现的 `current/previous` 是实体目录；蓝绿实现时应迁移为指向不可变版本的目录引用，真实旧版本仍保存在 `releases/`。每个运行容器直接绑定对应版本的真实绝对路径，不能绑定会切换的 `current` 后期待 JVM 或 Docker 自动重载。制品和版本引用位于项目目录内，不使用 `/root` 作为解压或备份目录。

继续只维护 `.env.server`、`.env.client` 两类用户环境文件；不增加需要用户手工编辑的蓝绿 env。槽位、版本号、制品绝对路径和唯一网络别名由发布器生成 Compose override，不改写共享凭据。日志和 journal 位于独立持久卷，不随版本目录删除，原卷名称保持不变。

## 3. 端口、网络与前端

| 入口 | 目标行为 |
|---|---|
| 控制台原 `FRONTEND_PORT`（默认 9090） | 常驻网关提供当前前端和 `/api/` |
| API 原 `SERVER_PUBLIC_PORT`（默认 8080） | 常驻网关代理活动 server 组 |
| SDK 原 `RUNTIME_SDK_PORT`（默认 7071） | 由常驻入口代理活动 runtime，蓝绿 runtime 不再各自绑定同一宿主机端口 |
| MySQL / Redis / Kafka | 原地址、认证、网络、端口及持久数据保持不变 |

两个 server 组使用不同的网络别名，例如 `server-blue`、`server-green`；网关不能继续用会同时解析到新旧组的通用 `server` 名称。候选组未通过检查前不加入生产 upstream。

网关挂载固定配置目录，通过目录内的原子文件替换发布配置。避免对单个 bind-mounted 配置文件做宿主机重命名后，容器仍读取旧 inode。应用版本目录同样通过稳定父目录供静态资源读取，禁止整个父目录被普通更新替换。

前端资源需要版本化 URL，覆盖 JS/CSS、Monaco、字体和地图等资源；每个资源路由只能映射到对应 `dist/`，不能暴露发布包中的 env、源码或迁移文件。旧页面可能存活很久，旧资源保留到定义的兼容窗口结束，旧页面调用的新后端 API 也必须向后兼容。只保留旧 JS 文件不足以解决接口不兼容。

## 4. 日常发布流程

操作入口继续保持上传两个文件和五行命令；蓝绿功能完成前，不提供会被误认为已可执行的蓝绿命令。计划继续复用 `deploy.py`，由发布器完成以下过程：

1. **准备**：获取部署锁，校验包及逐文件摘要，识别活动槽与版本；检查磁盘、内存、CPU、数据库连接数和迁移兼容声明。候选版本展开到新的 `releases/<release-id>`，旧文件不变。
2. **兼容迁移**：只执行经过审核、允许新旧应用并存的独立迁移；由一个执行者持有迁移锁。没有待执行迁移就跳过。需要维护窗口的迁移直接拒绝在线发布，不能自动改为停止服务后继续。
3. **启动候选组**：Blue 活动时启动 Green，反之亦然。采用不同制品路径和网络别名；必须避免候选实例在接流前自动改表或产生未授权的后台业务副作用。
4. **候选验收**：每个 server 副本 readiness 通过，完成规则、模型预热；校验版本标识和固定无副作用业务用例。SDK 校验规则同步和依赖连接，不能仅检查端口可连接。
5. **切流**：生成完整 API、SDK 与前端路由，执行 `nginx -t`，成功后 reload。通过固定入口验证实际返回的新版本，不能只凭 reload 命令返回 0 就认定切换成功。
6. **记录与排空**：确认切流后原子记录活动槽、current、previous 和待回收旧组。等待旧请求、网关旧 worker、异步日志与计费队列、消费者及 journal 达到约定的退出条件，再优雅停止旧组。
7. **完成**：记录验证结果与版本摘要。旧制品和迁移记录保留；普通发布不重启共享组件，不删除卷，也不清理运行中或 previous 引用的目录。

Nginx reload 会启用新配置的 worker，并让旧 worker 继续处理已有请求；这是平滑切换的基础，但不能在 reload 后立即停止旧 JVM。[Nginx 配置重载说明](https://nginx.org/en/docs/control.html)

排空必须使用请求/任务状态及明确的期限，而不是固定 sleep 若干秒。超时后保留旧组、记录待处理状态，不能强杀长请求后宣称无中断。Spring 的优雅关闭有时间上限，须与网关、外数调用、执行超时及日志刷新预算协调。[Spring Boot 3.5 优雅关闭](https://docs.spring.io/spring-boot/3.5/reference/web/graceful-shutdown.html)

网关继续关闭执行和写请求的自动上游重试，避免重复执行、名单修改或计费。请求幂等需要业务协议保证，不能靠代理重试伪装发布成功。

## 5. 失败与回退

| 失败阶段 | 处理要求 |
|---|---|
| 包校验、资源检查、候选启动或预热失败 | 不切流；旧组继续服务，只处置候选组 |
| 配置校验失败 | 不 reload；恢复磁盘上的原配置，避免下次重启读到无效配置 |
| 切流后的业务探测失败 | 数据与接口仍兼容时，切回旧组及对应前端；让已经进入新组的请求完成后再停止新组 |
| 旧组排空超时 | 新组继续服务，旧组保留并记录待回收；不强杀、不谎报全部完成 |
| 发布器中断或机器重启 | 根据持久发布状态、实际网关版本与运行实例核对恢复；不能只看磁盘配置推断流量已切换 |
| 数据库迁移不兼容或已产生不兼容数据 | 不自动回退数据库或启动旧代码；进入明确的维护与恢复流程 |

发布状态至少区分“准备、候选就绪、已切流、旧组排空、完成/失败”。同一时间只允许一个发布；排空或中断状态未处理时不能再次占用旧槽。current/previous 必须反映实际生效版本，不能把未接流的候选版本标成 current。

## 6. 当前代码需要补齐的能力

| 位置 | 现状 | 实施内容 |
|---|---|---|
| `scripts/deploy.py` | 先停应用，再替换 current 并重建 | 蓝绿槽位编排、发布状态、候选验收、切流、排空与回退 |
| `docker/docker-compose.server.yml` | web 与应用一起更新，所有 server 挂同一制品目录 | 网关常驻；每个应用组固定到自身版本；唯一网络别名 |
| `docker/docker-compose.client.yml` | 单 runtime 直接绑定 7071 | 固定入口接管端口，蓝绿 runtime 使用内部地址 |
| `docker/nginx/` | 固定 upstream 与单版 dist | 受控配置切换、版本识别、前端资源版本路由与保留 |
| `SchemaSyncService` / `schema.sql` | 启动期间会补表、改列、更新视图和执行维护逻辑 | 将版本迁移放到独立发布阶段；启动保留必要的只读兼容/安全校验，不能简单关闭所有检查 |
| readiness 与应用版本信息 | 已检查 DB、Redis、规则和 ONNX 预热 | 补充可核对的发布版本，以及业务探测和排空状态 |
| Kafka、账单任务、outbox、journal | 新实例启动后可能处理共享后台工作 | 验证跨版本协议及幂等；明确消费者/任务激活与归属交接，旧队列和 journal 处理完成后再退役 |
| 会话与前端 API | 已使用 Redis Session，但没有跨版本发布验收 | 验证登录态、权限版本失效、序列化和新旧客户端 API 兼容 |

特别注意：`SPRING_SQL_INIT_MODE=never` 只控制 Spring SQL 初始化，不能关闭 `SchemaSyncService.@PostConstruct` 的结构维护。旧版本重启还可能重新生成旧视图，因此不能直接假定任意旧 JAR 与新版兼容；应先建立支持在线发布协议的基线版本。

迁移采用先扩展、后切换、最后清理旧结构的方式。删列、重命名、改变字段含义和不兼容的视图变更不能直接伴随在线切流。即使在线 DDL 也可能申请排他元数据锁或被长事务阻塞，需要评估执行时间、锁等待和业务影响。[MySQL Online DDL 限制](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-limitations.html)

## 7. 资源预算

以下为当前 Compose 内存/CPU 上限的求和，不是实测峰值，不包含宿主机、NPM 和其他服务。需要使用实际负载、模型数量、连接池和预热行为再次验收。

| 组件 | 发布期间数量 | 内存上限合计 |
|---|---:|---:|
| server | 4 | 6 GiB |
| SDK runtime（可选） | 2 | 1.5 GiB |
| 固定网关 | 1 | 0.25 GiB |
| MySQL | 1 | 1.5 GiB |
| Redis | 1 | 0.375 GiB |
| Kafka | 1 | 1 GiB |
| 合计 | | **10.625 GiB** |

对应 CPU 限额之和约 2.9 核。16 GB / 4 核具有双版本并存的预算基础，但预热期间必须保留旧组处理流量的余量；预算或实际资源检查不通过时，应拒绝发布，不能通过停止旧组腾资源来冒充在线发布。

## 8. 现有环境如何过渡

1. 当前用户结构是外层 env 备份、内层 deploy-prod 运行。当前 `--adopt-layout` 只完成已实现的目录整理，会停相关服务，不能用来完成蓝绿入口迁移。
2. 先实现并验证本设计中的基线能力，再安排一次受控窗口完成目录整理、基线应用部署和网关接管原端口，尽量避免多次迁移。
3. 核对是否有调用方绕过网关直连 server/7071。现有单个容器独占端口时，不能直接启动另一个容器占同一端口；首次入口切换不承诺自动无感。
4. 保留原 MySQL/Redis/Kafka 项目、卷、密码及密钥；应用 journal 绑定原持久存储并使用明确的实例归属。蓝绿应用组可以新增独立项目，但不能依靠改基础设施项目名创建新数据卷。
5. 完成真实流量下的在线发布与回退验收后，日常更新才启用蓝绿流程。当前发布包仍按维护窗口方法使用，不提供不存在的 `--blue-green` 参数。

## 9. 验收条件与当前证据

隔离机制实验使用 Nginx + Python HTTP 服务：持续 952 次请求全部成功，测试端未发现重复执行；切流前的 5 秒慢请求由旧版本完成；网关容器未重启；错误配置未接管流量；新旧静态资源均可访问。该实验不包括真实 Java 规则、登录态、数据库迁移、TLS/NPM、SDK、HTTP/2 或长连接场景，不能视为生产无中断验收。

实施后至少验收：

- 连续真实规则请求、无副作用固定用例及关键页面在发布/回退期间无新增连接错误或 5xx。
- 通过 Trace/事件 ID 核对实际执行、名单动作和账单，不能仅检查 HTTP 200；不重复执行、不重复计费。
- 新组启动失败、规则或模型预热失败、网关配置失败时旧组仍持续服务。
- 长请求、上传、异步持久化及必要长连接完成后，旧组才退出；超时路径可观察并保留现场。
- 登录与权限校验跨版本正常，旧页面延迟加载旧资源不出现 404，新旧客户端接口兼容。
- 新旧应用并存及旧版本重启不会意外改坏结构或视图；不兼容迁移被发布前置检查拒绝。
- SDK 同步、执行及日志上报连续，Kafka 重平衡/后台任务交接不产生业务重复或未解释的丢失。
- 发布器在每个阶段中断后能根据实际生效状态恢复，current/previous 和路由一致。
- 两种现代 Compose 命令均通过，原项目数据和端口保留，服务器资源峰值有余量。

上述验收完成前，当前生产更新仍按 [维护窗口部署流程](server-upload.md) 执行。
