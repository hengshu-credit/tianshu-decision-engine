# 规则设计器操作、版本引用与审批改造设计稿

状态：用户已确认“实施”，按实施计划推进；本文件不是功能已实现或已通过测试的声明。计划见 `docs/superpowers/plans/2026-09-14-designer-actions-versioning.md`。

## 1. 已确认需求

- 九类设计器操作统一为：编译、保存、发布、测试。
- 进入设计页不创建草稿；无改动切版直接加载目标内容。有改动切版时提供“保存并切换”“不保存直接切换”和取消操作；只有选择保存才写草稿。
- 同一规则允许保留多份草稿，草稿可以删除；草稿标识与正式版本号分离，正式版本号只在发布审批通过、实际生效时生成。
- 正式（生产）版本的改动保存为新草稿，不直接修改正式版本；已有草稿的改动由用户选择“新增草稿”或“覆盖当前草稿”。
- 编译、测试不保存规则配置；用户点击保存、发布，或切版时选择保存才写草稿。
- 规则名称下方的信息行：引用字段信息在最左，规则状态在最右。状态不再占用操作按钮行。
- 按钮背景、文字、边框、hover、聚焦、加载与禁用表现统一适配明暗、自定义纯色及渐变主题，不固定使用白字或固定状态色。
- 指定版本引用保持指定版本；未指定默认使用最新版，并跟随最新已发布版本变化。新版本不强制迁移指定版本引用。
- 发布时选择覆盖已有版本或新增版本，确认后保存并提交审批；审批通过前不影响当前生效规则。
- 测试复用原参数输入、结果和执行追踪界面，不再要求先保存或先完成编译检查才能点击。
- 修复设计器及审批页未处理异常，并追踪截图中的实际后端错误，不通过屏蔽 console 或吞掉失败来验收。

## 2. 四个操作的边界

| 操作 | 输入与执行 | 持久化及结果 |
|---|---|---|
| 编译 | 当前页面配置 → 对应模型编译器 → 实际 QLExpress 脚本及语法检查 → 可适用于当前配置的发布前规则校验 | 返回脚本、问题路径和校验结果；不写草稿、版本或审批申请 |
| 保存 | 当前页面配置先编译，语法及模型编译成功后保存 | 正式版本改动新建草稿；草稿改动由用户选择新增或覆盖当前草稿，不生成正式版本号；发布前治理检查存在阻断项时仍可保存合法草稿，并明确提示尚不可发布 |
| 发布 | 编译、校验、保存 → 选择新增/覆盖及变更说明 → 确认 → 保存发布选择并提交该草稿审批 | 配置未变不重复保存模型；审批申请冻结模型摘要、编译结果、目标版本和依赖证据；审批通过后才激活对应版本 |
| 测试 | 点击即可打开现有测试界面，实际运行时以当前配置临时编译，并用输入参数执行 | 不写规则草稿/版本；保留现有测试日志、调用记录及追踪行为 |

编译或保存失败时不显示成功、不提交审批，保留页面修改。仅发布前治理校验失败不应被误报为 QLExpress 语法失败。测试不受“未保存/未检查”状态禁用；尚未加载内容、无执行权限或重复点击正在进行的请求时给予明确反馈，不绕过后端权限。

每次请求携带当前规则/来源标识与配置摘要。用户编辑或切版后，旧响应不得覆盖新内容、标记新内容已编译或把旧结果当成当前结果。发布弹窗打开期间若配置变化，必须重新编译校验并更新待提交内容。

### 多草稿保存与标识

按当前编辑来源区分保存行为：

- 正式（生产）版本或初始内容有改动：保存产生新的草稿 ID，原正式版本及已有其他草稿不变，不出现覆盖正式版本的保存选项。
- 当前来源为草稿且内容有改动：明确提供“新增草稿”和“覆盖当前草稿”两种方式。新增产生新的 ID 并保留原草稿；覆盖仅更新当前草稿的内容、编译结果、摘要和保存时间，保持该草稿 ID 不变，不增加草稿数量。
- 覆盖必须携带当前草稿 ID 与已加载的锁版本，服务端重新核对 DRAFT 状态、归属和编辑权限。并发修改、删除或提交审批造成冲突时，保留页面内容并提示处理，禁止覆盖另一份草稿、自动刷新锁后重试或更新已提交内容。
- 当前草稿内容未变时直接复用，不重复提示保存方式或创建草稿；发布前已经保存同一内容也不重复写入。有改动的发布前保存和切版前保存遵守相同来源规则，不因流程不同默认为覆盖。
- 保存成功后当前编辑来源指向实际保存的草稿 ID（新增时更新、覆盖时不变）；切版前保存则继续进入用户预先选择的目标。取消保存方式选择时留在当前页面并保留修改。

多份草稿可并存，不再因其他草稿存在而报错或要求覆盖它。草稿是可编辑的工作记录；提交审批后的冻结内容、正式版本快照及制品不可用草稿覆盖接口修改。覆盖操作留有审计事件，其他草稿已有内容及其创建时的来源证据不随源草稿覆盖而改变。

草稿展示为“草稿 · 内部编号 / 保存时间”，并可查看基于哪个来源创建。内部编号仅用于区分草稿，不使用正式 v1/v2 标签，不消耗正式版本号。版本选择器区分“已发布版本”和“草稿”；审批记录保持单独状态。

删除“每规则仅一份草稿”的服务层校验及相应前端假设。新建操作携带幂等标识，防止重复点击或响应重试产生多份相同操作的草稿。覆盖保存、提交审批、删除等状态变更按明确草稿 ID 和乐观锁执行，禁止根据规则 ID 随意选择一份草稿操作。同一规则的审批串行约束不扩大为禁止保存其他草稿：已有审批时仍可编辑、保存和删除其他未提交草稿，提交第二个发布申请时明确告知需等待当前审批结束。

### 设计页切换版本

- 没有未保存修改：直接读取所选正式版本或草稿，无确认框、无写请求。
- 有未保存修改：弹窗提供“保存并切换”“不保存直接切换”；关闭弹窗或取消则留在原页面，保留修改。
- 保存并切换：正式版本改动新建草稿；草稿改动在同一个切版确认框内提供新增/覆盖保存方式，避免连续弹出两个确认框。保存成功后再加载用户最初选择的目标，不要把保存结果当作切换目标，也不要重复弹出离开确认。
- 编译或保存失败：留在当前页面，保留修改和目标选择意图，展示可理解的原因；不以保存成功的状态跳走。
- 不保存直接切换：只放弃当前页面未保存的修改，直接加载目标内容；不删除、不改写任何已存在草稿。
- 保存期间锁定本次切版操作，防止重复请求或较晚响应覆盖另一个目标。目标读取失败维持现有页内重试，不自动创建草稿。

### 草稿删除

- 在草稿管理入口提供单份草稿删除，按草稿稳定 ID 操作；正式版本和审批中记录不提供该入口。
- 删除前确认所选草稿，若删除的是当前正在编辑的草稿，同时明确会放弃其页面未保存修改；取消则内容和来源保持不变。
- 服务端再次校验所属规则/项目、编辑权限、DRAFT 状态和锁版本；已提交、已批准、已发布记录不能通过草稿删除接口移除。
- 采用逻辑删除，从正常草稿列表移除，但保留审计事件及来源记录，避免其他草稿的来源链断裂；不引入自动清理或物理清空历史数据流程。
- 删除非当前草稿不切换当前编辑内容；删除当前草稿成功后优先显示最新正式版本，没有正式版本则选择其余最新草稿，都没有则显示初始内容，不创建替代草稿。
- 并发删除/提交或接口失败时给出明确提示，不能错误显示删除成功或静默放弃当前修改。

## 3. 版本模型与引用生效

### 方案比较

推荐“稳定业务版本绑定 + 不可变修订制品”：业务版本 v1/v2 指向经过审批的具体修订和制品，覆盖只更新绑定，原记录和制品保留。规则调用显式区分指定版本和最新版。

另一种方案是每次发布都修改所有父规则并重新发布整个依赖链；它会增加审批和连锁发布成本，而且容易把指定版本误改成最新版，不采用。直接覆写历史制品则破坏摘要、审计和历史执行追溯，也不采用。

### 业务版本与物理记录分离

- 引入具有稳定 ID 的业务版本绑定，包含规则 ID、业务版本号、当前生效修订/制品、绑定代次和状态。
- 已提交/发布的 `RuleRevision` 冻结内容、制品内容/摘要、审批历史及原始发布快照保留，不通过更新历史脚本正文实现正式版本覆盖；尚未提交的 DRAFT 允许用户明确选择覆盖保存。
- 新增版本：在审批通过、实际生效的事务中锁定规则并生成下一个正式业务版本号、激活新绑定、更新最新版指向。创建/保存/删除草稿、提交或驳回审批均不消耗正式版本号。未指定版本的调用自动使用新版本；指定其他版本的调用不变。
- 覆盖版本：审批通过时将目标业务版本绑定切到新修订。所有指定该业务版本的调用使用覆盖后的内容。
- 如果当前最新版是 v3，覆盖 v1 只影响指定 v1 的调用；默认最新版仍是 v3。若覆盖的是 v3，指定 v3 和默认最新版都获得覆盖后的内容。
- 提交审批时冻结新增/覆盖方式、覆盖目标及绑定代次、来源和依赖证据；新增方式此时不分配正式版本号。覆盖目标或审批基线在等待期间变化时标记冲突并要求重提；实际激活时采用事务锁和唯一约束避免版本号重复。

### 引用结构与运行时

- 规则关联继续使用稳定规则 ID；业务名称、编码仅作展示，不作为新关联键。
- 引用配置提供“最新版（默认）”及明确业务版本选项；持久化引用模式和指定版本绑定 ID。现有缺少版本配置的调用按最新版兼容。
- 编译器生成带版本策略的规则调用；前端配置、核心编译器、服务端执行与客户端 SDK 同步支持，不能只修改下拉框。
- 原有制品包含嵌套规则快照。新制品需记录引用策略；生产执行按对应绑定解析目标制品，而不是永久沿用父制品内已经过期的子规则副本。
- 一次执行中的同一规则及引用策略锁定同一解析结果，避免执行中途发布导致前后调用使用不同修订。日志记录实际业务版本、修订、制品摘要及绑定代次，保证变化可追溯。
- 服务端发布事件与客户端同步携带版本绑定变化；缓存键与失效按规则 ID、业务版本绑定和代次区分。缓存命中时不需要每次调用额外远程查库；正常推送和补偿同步沿用现有机制。不能承诺网络断开客户端瞬间得到更新。
- 不存在、不可用或跨项目无权限的指定版本明确报错，不回退为最新版。循环调用校验同时覆盖指定版本和最新版更新后的依赖，防止 B 发布后使既有 A → B 形成新环。
- 审批前展示受影响调用方并校验字段/输出契约；不兼容变更阻断生效，不能让调用方在无提示情况下执行失败。
- 本地导入、部署和 SDK 同步必须保留稳定 ID 绑定、引用策略与实际制品摘要；旧制品中的历史执行证据不被重写。

## 4. 前端布局与异常处理

### 布局

第一行保留规则名称、版本选择和设计器自身工具，四个操作顺序固定为“编译、保存、发布、测试”。第二行采用左右布局：左侧引用字段信息，右侧当前编辑/编译/保存状态。窄窗口允许自然换行，不覆盖或挤压按钮。

发布作为主操作，编译、保存、测试采用清晰可区分的次操作样式；复用项目主题令牌和现有按钮体系。状态使用主题语义色与文字，不只靠圆点颜色传递含义。非必要加载/只读提示维持页内 info，无模态遮罩。

### 错误处理

- 在用户操作边界统一接住异步异常；请求层已提示的错误不重复弹出，取消操作不记作错误。错误原因仍保留可诊断信息，不用全局拦截把异常吞掉。
- 编译与保存解耦，消除“点击编译却因为已有草稿而失败”的现有链路。
- 审批页处理请求失败，保留评论和当前操作状态；后端定位导致事务 rollback-only 的首个异常，保持业务更新、审批状态及发布事件的一致事务语义，禁止无条件 `noRollbackFor` 或单纯隐藏最终异常。
- `reportAllChanges/startTime` 的匿名脚本来源需在实际浏览器追踪；目前不能认定由项目业务代码或浏览器扩展产生。若确认外部注入来源，应如实报告并区分，不改业务逻辑掩盖它。
- `wheel` 的 non-passive 提示与未处理异常分开检查；涉及画布缩放且需要 `preventDefault` 的监听不能盲目改为 passive。

- `RuleGovernanceSubmissionService`、`GovernanceApprovalService`、`RuleLifecycleService`：现有规则提交审批与生效链路。

## 6. 验收标准

1. 九类设计器的编译均展示真实 QLExpress 代码及规则校验结果；编译后数据库无新增/更新草稿、发布或审批记录。
2. 保存先编译，多个不同来源的草稿可共存。正式版本改动只生成新草稿；草稿改动选择新增时新 ID/原内容保留，选择覆盖时 ID 和数量不变且仅当前草稿更新；取消和冲突均保留页面修改，重复请求不重复创建，不产生“已有草稿”未处理异常。
3. 未保存的有效配置可直接测试，结果确实来自当前页面配置；语法错误、参数错误、运行失败都在现有结果界面明确展示，旧测试流程与追踪保留。
4. B:v1/v2、A 指定 v1、C 使用最新版：新增 v2 后 A 仍调用 v1、C 调用 v2；覆盖 v1 后 A 使用新 v1、C 仍用 v2；覆盖 v2 后 C 使用新 v2。
5. 审批未通过不改变执行结果；审批通过才切换绑定；并发覆盖/新增、依赖变化、循环和不兼容契约不会静默发布。
6. 服务端及 SDK 测试验证指定/默认、嵌套依赖、缓存命中/失效、推送遗漏补偿与实际版本追踪，不仅检验管理页面显示。
7. 名称下方左字段右状态，四按钮全部主题状态可读；明暗、自定义浅/深主色、渐变与窄窗口浏览器验收。
8. 用真实 UI 复现截图中的应用异常并重走编译、保存、发布审批、测试；模拟 API 只用于确定性异常/并发/主题用例，不能代替真实数据库审批及发布验收。
9. 完成前执行前端 dev 页面检查并停止本次验证进程、全量单测、lint、生产构建、浏览器回归；后端全模块构建、服务启动、全量测试。保留其他任务的改动，不重启或停止不属于本次验证的服务。
10. 有改动切版的保存/不保存/取消三条路径结果正确；正式版本保存新建草稿，草稿保存按所选新增/覆盖执行。保存失败不跳转，成功后进入原定目标，无重复写入、无二次离开确认，无改动切版没有写请求。
11. 保存多份草稿、删除草稿或驳回审批均不消耗正式版本号；新增版本仅生效时分配，覆盖版本沿用原正式版本号。并发激活没有重复编号。
12. 删除当前/非当前/最后一份草稿、取消删除、并发提交、无权限、已发布记录删除请求都有覆盖；其他草稿、正式版本、审计及来源引用不受破坏。
