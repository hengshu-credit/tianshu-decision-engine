## 1. 审计结论

天枢已经具备可交付决策平台的主体能力：九类规则设计器、变量与数据对象、外数 API、数据库查询、名单、模型、函数、规则测试、表达式追踪、审批发布、版本回滚、实验、账单、开放 API、Java SDK 和 HTTP-only SDK 均有对应代码入口。当前主要问题不是缺少模块，而是模块之间的“完成证据”没有统一起来：用户能保存配置，却不一定知道它是否能测试、是否已进入审批、线上执行的到底是哪一个修订；运维能看到失败日志，却缺少队列、版本、依赖和容量的同一条证据链。

本次审计以实际代码和页面为准，未把旧规划中的“待实现”项目当作事实。产品边界保持不变：一级菜单平铺，SQL 能力继续直接提供，变量/模型/规则引用只使用稳定 ID，`ref_type` 显式区分变量和模型，导入字段名与用户编码原样保留，发布制品冻结依赖。

## 2. 当前使用链路与复杂度

一次新规则从创建到线上调用通常要经过：

```text
项目/权限 → 数据对象或变量 → 外数/数据库/名单/模型 → 规则输入输出
→ 九类设计器 → 保存/编译 → 自动生成测试报文 → 测试与追踪
→ 提交审批 → 批准 → 发布制品 → 开放 API / SDK 调用 → 日志与账单回溯
```

熟悉变量编码、数据类型和 SQL 的策略人员可以完成其中大部分配置。首次接触系统的业务人员仍需要自己判断以下概念的关系：数据源与接口、接口与 API 变量、对象字段与变量、保存内容与生命周期修订、测试版本与发布版本、请求预览与真实外数调用。当前页面多数提示是字段级或 toast 级，不能在失败后给出唯一下一步，因此配置复杂度主要来自流程分散，而不是规则表达能力本身。

## 4. 问题清单与证据

### P0：执行可用性与发布证据没有统一闭环

`RuleDetail.vue`、九个设计器、`RuleTest.vue`、审批页和开放 API 各自展示保存、编译、测试、审批、发布状态。用户必须手工拼接这些状态，无法看到“当前修订是否可测试”“测试证据是否属于当前修订”“线上制品摘要是否与执行日志一致”。发布预热失败时，服务可能已经启动，但管理端和 readiness 未必阻止调用。

**需求：**增加统一 `readiness/preflight` 协议，每条问题包含 `code、severity、path、title、message、nextAction、resourceId、revisionId`；规则详情、设计器、变量/外数/数据库页面复用同一报告；发布、SDK 执行和日志均显示 `revisionId + artifactDigest`。

**验收：**缺输入、引用停用、未编译、测试过期、审批未通过、制品预热失败分别可定位；每种阻塞只给一个主操作；同一修订在测试、审批、发布、执行日志中可追溯。

### P1：配置流程对首次使用者过长

项目、资源、规则、测试和审批分散在一级菜单。一级菜单必须保持平铺，但每个资源详情页需要显示可收起的业务进度：基础信息 → 依赖 → 映射/脚本 → 预览 → 测试 → 审批生效。外数、数据库、变量和模型详情现在共用“已保存配置预检”面板；变量编辑器只在已有变量 ID 时允许检查，避免把新建草稿误当成已生效配置。

**需求：**做“流程引导层”，不改变路由和后端提交结构；每一步可以跳转到对应 Tab 或设计器节点，失败时保留用户输入和当前上下文；保存、送审、发布按钮旁明确动作边界。

**验收：**策略人员只看页面提示即可完成一个输入变量、一个外数变量和一条规则的闭环；关闭/切换页面时未保存内容有明确提示；没有自动覆盖其他草稿。

### P1：外数测试的真实副作用此前不够显眼（本轮已修复）

`ExternalDatasourceController` 的 `/api-config/{id}/invoke-preview` 会调用 `externalApiInvokeService.invoke(config, params)`，是真实网络调用；`/request-preview` 才是无网络报文预览。原 `ApiDetail.vue` 只在工具栏放置“执行测试”，费用和副作用边界不在按钮附近。

**本轮修复：**在接口测试区加入明确的风险提示，说明真实访问、供应商费用和业务副作用，并指向“生成请求预览”；新增组件测试覆盖该文案。

**后续需求：**将预览、沙箱调用、生产调用分为三种明确模式；生产调用需要显示数据脱敏和费用确认；每次测试记录调用者、配置摘要、请求摘要和供应商响应摘要。

### P1：自动生成报文有能力，但诊断没有统一到所有入口

`RuleTestSchemaService` 能根据外部输入生成嵌套样例，能识别父子路径冲突；API 页能从对象、映射、鉴权和异步轮询配置收集路径。变量在线测试、模型测试、规则测试和 API 测试的样例保存结构仍不一致，用户在不同页面重复输入同一份报文。

**需求：**建立统一测试样例模型：`caseId、scope、targetType、targetId、revisionId、params、expected、traceMode、createdBy`；生成器返回字段路径、类型、来源、默认值、是否必填和诊断；支持从上游对象/变量一键生成规则、模型和 API 的样例。

**验收：**对象字段、API 参数、衍生变量和模型入参能在同一报文树中展示；路径冲突、缺失必填、类型不匹配在字段位置显示；样例绑定修订后，规则修改时标记过期而不是静默复用。

### P1：数据库/衍生变量/数据对象的配置语义仍需要更强的可解释性

系统已经按 ID 保存数据对象字段和变量引用，执行时也有依赖计划和根执行缓存。页面仍要求用户理解“输入字段”“引用变量”“对象路径”“衍生来源”和“结果映射”的差异。SQL 参数目前主要依赖位置，结果路径和类型冲突需要进入测试后才能发现。

**需求：**SQL 编辑器旁提供参数绑定表（第 N 个 `?`、来源 ID、脚本路径、类型、样例）；结果预览显示行数、字段路径、推断类型和空值策略；衍生变量显示依赖图和纯计算/外部来源标签；对象字段变更先做影响分析。

**边界：**继续允许有 SQL 能力的业务人员直接编辑 SQL，不隐藏 SQL；只允许查询类语义，写入、多语句和锁定查询在连接打开前拒绝。

### P1：开放 API 文档需要成为可执行契约

项目文档导出包含认证元数据、规则输入输出、样例和代码示例，在线 runner 还支持直接发起请求。当前需要用户自行拼接外层响应、业务结果、错误码和 trace 状态；文档与 SDK 的服务端执行/本地执行边界曾出现不一致。

**需求：**导出 OpenAPI 3.1 与人读 HTML 两种格式；每个接口固定展示请求字段、映射来源、必填/类型、响应路径、错误码、幂等键、超时和 trace；在线 runner 默认只生成 curl/请求预览，真实发送需显式切换到测试环境；绝不导出 token、密码、API key 或签名密钥。

**验收：**文档中的 curl、Java、HTTP-only SDK 对同一规则返回相同 envelope；网络超时明确为 `UNKNOWN` 并提供 trace 状态查询；相同幂等键请求体不同返回 409；文档导出不含任何秘密字段。

### P1：追踪树与生产日志缺少预算化策略

测试页默认展示树和 JSON，服务端 `RuleExecuteService` 可把追踪写入执行日志，开放 API 也可按契约记录/返回 trace。复杂规则、嵌套规则和外数响应会放大 JSON 序列化、网络响应和数据库写入。

**需求：**提供 `OFF / SUMMARY / FULL` 三档追踪；生产默认 SUMMARY；FULL 受项目级大小、节点数、字段脱敏和采样率限制；输入、外数请求头、响应中的敏感字段按变量/路径策略遮罩；超过预算返回截断原因和 traceId。

**验收：**同一请求的结果不因 trace 模式变化；P95/P99 统计分 trace 档位；日志页面能区分“未采集”“采集后截断”“无权限查看”。

### P1：异步持久化已开始，但队列满时会回退到请求线程

`DecisionExecutionPersistence` 使用有界队列和单写线程，把根日志和计费移出请求线程；队列满时优先 fsync 到本地恢复 journal，journal 不可用才同步回退，避免正常高峰把数据库慢写传回请求延迟。当前已有 `queueDepth、journalQueued、fallback、failed、avgWriteMs` 指标；`overflowStrategy` 明确报告 `JOURNAL_THEN_SYNC_FALLBACK` 或无 journal 时的 `SYNC_FALLBACK`，仍需在生产拓扑中建立按项目/规则版本的告警和容量门槛。

本轮进一步把日志和计费写入拆成两个独立重试单元：日志写入失败不会阻断计费，计费失败不会重复写日志；指标新增 `logFailed` 与 `billingFailed`，看板分别展示两类失败。事件级 `persisted/failed` 总状态保持不变，仍可识别部分成功事件。

**需求：**日志和计费拆成可恢复 outbox；请求线程只写轻量事件或内存缓冲；队列满时按明确策略写入本地恢复 journal，journal 失败才同步回退或返回可重试错误，不能静默改变 P95；增加持久化延迟、溢出、丢弃/降级计数和告警。

### P2：横向扩容和高并发仍缺少跨节点容量契约

开放规则执行线程池默认按 CPU 设置，每节点队列 1000；来源解析默认属性为 4，未配置时代码回退为 1；Redis、MySQL/Hikari、外数连接池和模型执行池分别限流。节点级保护存在，但项目级 QPS、外数供应商配额、全局并发、熔断状态和日志队列没有统一的共享预算。

**需求：**为项目、规则、外数数据源和模型定义共享限流/并发预算；Redis 使用原子令牌或滑动窗口；拒绝响应带 `Retry-After、queueDepth、limitName`；管理台显示节点、项目和资源三层利用率；压测覆盖冷缓存、热缓存、外数超时、Redis 断连、MySQL 慢查询、模型超时和日志积压。

**验收：**新增节点后吞吐按预期提升且不重复计费；Redis 重连、推送乱序和节点重启后客户端最终收敛到同一制品；未知网络结果可查询状态，不自动盲目重放外部副作用。

### P2：启动就绪状态应包含规则预热结果

QLExpress 预热和依赖加载失败不能只写日志后继续把服务视为“可用”。已发布制品、函数和模型的可执行性应进入 readiness 和管理台。

**需求：**启动阶段输出制品数量、成功/失败数量、失败资源和摘要；关键规则预热失败时 readiness 为非就绪或明确降级；支持按规则/制品手动重试和恢复。

## 6. 统一验收方法

1. **代码门禁：**前端 `npm run dev` 启动无错误、`npm run lint`、`npm test`、`npm run build`；后端 `mvn clean install -DskipTests`、`mvn spring-boot:run`、`mvn test`。
2. **页面门禁：**从浏览器完成真实页面操作，不能通过数据库写入跳过数据源、变量、规则、审批或发布步骤；检查失败重试、离开保护、权限和版本切换。
3. **契约门禁：**自动生成报文、API 预览、真实外数调用、数据库参数、衍生变量、对象字段、开放 API、HTTP-only SDK 和完整 SDK 使用同一组输入/期望结果。
4. **可靠性门禁：**压测执行线程池、来源解析、外数连接池、模型池、日志队列和 Redis 推送；注入超时、断连、乱序、重复请求和节点故障。

- 新增离线配置迁移包：用户请求时生成独立 `TIANSHU_RESOURCE_TRANSFER` ZIP，按稳定 ID 递归带出治理上游依赖，名单只导出配置不带记录；导入预检、全局/项目目标范围、字段策略、治理快照冲突预览和目标写入已接入。项目级导入要求显式绑定目标项目、提供源项目映射或勾选新建项目；新建项目会生成目标 Token 并初始化治理基线。固定版本默认保持草稿，显式开启发布选项后按目标业务版本号重建绑定并取最新代次；目标缺少较老业务版本时明确阻断，完整跨环境执行回归待真实环境验证。
- 本轮回归修复：子规则入参绑定改为原地处理，保留共享会话中的对象引用；缺失数据对象字段不再提前写入 `null`，允许源变量继续组装；运行时为 QL 上下文增加可嵌套绑定，父规则可立即看到子规则写入；子规则执行前校验冻结函数绑定，未知函数不再静默返回 `null`。嵌套规则、对象映射、流程变量和冻结函数回归均已覆盖。

本轮未把无法在无真实业务环境下证明的容量、备份恢复、跨节点故障接管和外数供应商配额一致性标记为已完成；这些必须在测试/生产拓扑中按第 6 节门禁执行。

## 9. 复核后仍需落实的明确缺口

1. **缺失与显式 null 的生产核对。**代码和自动化回归已覆盖根规则、子规则、延迟对象字段和模型投影；仍需在真实生产数据源中核对显式 null、字段缺失和多级对象映射的业务约定。
2. **“不保存大字段”的全链路核对。**`saveOriginal=false` 已覆盖主调用 Trace、attempt 日志、汇总日志、缓存命中/过期缓存和异步轮询/回调最终响应；留存处理失败仍回退保存原文。仍需在真实生产配置中核对鉴权日志副本，确保供应商密文和超大字段都按部署策略留存。
3. **数据库整体故障时的日志保障。**已增加可配置的本地 NDJSON 写前日志：日志/计费写入和数据库恢复 Outbox 同时失败时先 fsync 到 `RULE_EXECUTION_PERSISTENCE_JOURNAL_DIR`，数据库恢复后逐条重放，部分成功只保留未完成侧；坏行不会被自动删除。仍需在目标生产盘完成断电、磁盘满、节点重启和多节点共享目录演练，不能把本地盘方案当作跨节点复制或备份。
4. **生产验收闭环。**规则 17/28 已完成真实控制台修复和发布，且启动预热不再报错；执行日志新增受权限保护的离线回溯接口，缺失来源会显式返回告警且不访问线上数据源。仍需在目标生产拓扑完成外数日志回溯、Redis 恢复、容量、备份和灾备演练。

5. **留存清理生产演练。**日志清理器默认关闭，生产必须明确设置保留天数并在备份、归档、恢复演练后启用；清理任务当前不覆盖数据库整体故障下的恢复 Outbox。

6. **留存可观测性。**清理快照仍保留在 `GET /api/rule/ops/execution-metrics` 供运维接口使用；执行指标面板不展示清理入口。账单、规则执行、外数/模块调用、模型评分、数据库/名单调用、生命周期/名单变更和分流实验数据已从自动清理白名单移除，生产仍需核对备份和清理任务的执行顺序。

7. **脚本函数依赖冻结。**制品依赖闭包现在扫描编译 QL 脚本中的外部函数调用，并按项目/全局作用域冻结函数；未来发布会在制品生成阶段拒绝未绑定函数。规则 28 已重新发布为包含 `roundTax` 稳定函数绑定的制品，后续旧制品仍保持不可变。

8. **离线规则回溯与运维权限。**执行日志详情支持“回溯”：有 `revisionId/artifactDigest` 且制品仍存在时优先按历史不可变制品执行，避免后续发布改变历史分析；旧日志或制品缺失时才回退当前发布版本并明确告警。回溯基于历史请求、历史字段、外数/数据库/名单/模型调用日志构造离线执行，缺失来源写入 `missingSources` 和告警，不会调用线上数据源、写入新日志或产生账单。`/api/rule/ops/execution-metrics` 与预热重试接口改为显式 `rule:view`/`rule:submit` 权限，避免 `/ops` 路径被权限拦截器误判为缺失映射；首页不再展示指标面板，指标接口保留给受控运维调用。
