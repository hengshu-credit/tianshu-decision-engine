# 天枢决策引擎 UI 与配置流程评审（2026-10-01）

## 1. 结论先行

天枢当前的视觉基础已经达到可以持续迭代的程度：一级菜单平铺、项目上下文、页签工作区、主题令牌、浅色/深色模式、键盘焦点、表格列设置、发布六步进度、分层配置引导和校验定位均已有实际代码。继续堆叠颜色、卡片或新导航不会明显降低配置成本。

真正影响业务人员完成任务的因素是跨模块流程被拆散后，用户需要自己拼接以下事实：当前配置属于哪个项目和哪个修订、还缺哪一步、错误应去哪里修复、测试是否仍适用于当前修订、发布后线上执行的到底是哪份制品。下一轮 UI 应围绕“一个上下文、一个主下一步、错误可原位修复、草稿可恢复、状态可追溯”推进。

本评审保持以下产品边界：

- 一级菜单继续平铺，不引入“专家模式”或二级菜单替代现有入口。
- SQL 继续直接可编辑，面向 SQL 能力用户增加参数绑定、结果预览和安全提示，不隐藏 SQL。
- 变量、模型、规则引用继续只使用稳定 ID；展示名称变化不能破坏引用。
- 用户输入的编码、字段名和导入内容原样保存，不用 UI 优化之名自动改名或补写脚本名称。
- 已发布制品继续冻结依赖；界面只展示和引导，不绕过生命周期创建快捷发布路径。

本轮已落地一项可验证的视觉修复：浅色主题的警告实心按钮改用深色前景，修复“验证规则”按钮对比度不足的问题；同时保留原有警告背景、Hover、Active 和危险操作语义。

## 3. 目标用户与任务边界

### 3.1 业务策略人员

他们需要独立完成变量选择、条件、动作、评分、测试样例和规则送审。页面应把“业务含义”和“技术值”同时展示，例如显示“人脸活体分数 `livenessScore`”，而不是只显示编码。需要知道未命中、多条命中、默认分支和端点是否包含，但不需要先理解数据库表结构或制品解码。

### 3.2 SQL 型分析人员

他们可以直接写 SQL。页面要减少位置参数、结果路径和空值策略的重复理解，提供参数绑定表、请求预览、返回结构和类型诊断。JSON 完整配置保留为高级入口，不能被简单表单替代。

### 3.3 接入与运维人员

他们关心数据源鉴权、超时、重试、缓存、制品、项目令牌、同步、日志和容量。页面必须清楚区分“生成请求预览”“沙箱调用”和“真实外部调用”，并展示修订、制品摘要、请求来源和失败后的可恢复动作。

### 3.4 审批人员

他们需要快速回答：改了什么、影响了谁、测试是否针对本次修订、批准后何时生效、失败如何回滚。审批页不应要求审批人重新打开多个资源页面拼接证据。

## 4. 推荐的配置主线

保持一级菜单平铺，在页面内容区建立连续的业务主线：

```text
项目上下文
  → 准备变量/数据对象/外数/数据库/模型
  → 新建规则并选择模型类型
  → 输入字段与输出字段
  → 设计规则并保存草稿
  → 生成或编辑测试样例
  → 编译与发布前校验
  → 提交审批、批准、发布
  → 查看制品/修订/同步状态
  → 追踪实际执行与账单
```

每个详情页顶部都应显示一条轻量上下文带：`项目名称 / 资源名称 / 当前修订 / 草稿状态 / 最后保存时间`。顶部只保留一个主下一步按钮，其余操作降为普通按钮或更多菜单。跨页面跳转应携带返回位置、项目 ID、资源 ID 和修订 ID，返回后保留草稿和筛选状态。

## 5. 优先级最高的流程改进

### P0：统一校验和下一步协议

所有规则、变量、模型、外数和数据库测试/预检结果采用同一结构：

```text
severity, code, title, message, path, nextAction,
resourceType, resourceId, revisionId, location
```

界面规则：

1. 先显示业务标题和原因，再显示技术路径和错误码。
2. 每个阻断项只给一个主修复动作，例如“去变量管理启用字段”或“定位到第 2 行条件”。
3. 能定位时原位打开对应 Tab、表格行、条件行或设计器节点；不能定位时给出明确手工路径。
4. 修复后允许在当前上下文重新校验，不能要求用户重新填写表单。
5. `loading`、`failed`、`unknown`、`blocked`、`ready` 使用文字和图标表达，不能只依赖颜色。

### P1：规则创建后继续配置

创建规则时保留“仅创建”和“创建并继续配置”两个动作。成功后使用接口返回的规则 ID 进入对应详情或设计器，不通过名称搜索。创建请求期间锁定按钮；校验或网络失败时保留输入；创建成功但后续加载失败时提供“重新打开刚创建的规则”。

规则详情继续使用现有六步发布进度，但每步增加：

- 当前修订号和内容版本；
- 完成证据，例如输入字段数量、编译时间、测试通过时间；
- 唯一主动作；
- 阻塞原因和受影响资源。

### P1：测试证据绑定修订

测试样例和执行记录至少显示规则 ID、修订 ID、依赖摘要、输入、预期、实际、技术执行状态、业务断言状态和执行时间。规则或依赖变化后，旧证据标记为“对当前修订过期”，仍允许回看，不静默覆盖。

### P1：数据库变量可视化参数和结果

保留 SQL 编辑器，在编辑器旁提供参数表：`第 N 个 ? / 值来源 / 类型 / 预览值`。预览结果显示行数、字段路径、推断类型和空值策略；用户可以从结果表选择返回字段或路径。明确单值、对象、列表、零行、多行、字段缺失、类型不匹配、SQL 失败和超时的行为。

前端与查询页复用同一 SQL 分析结果，禁止表单和 JSON 两套逻辑产生不同参数顺序或丢失字段 ID。只读 SQL 规则继续由后端最终裁决，前端提示应解释原因而不是仅提示“格式错误”。

### P1：外数测试分为三种模式

外数页面同时存在“生成请求预览（不访问网络）”“沙箱调用”和“真实调用”。真实调用按钮附近显示网络访问、费用、供应商副作用、脱敏和审计说明；请求预览可以在没有供应商的情况下先完成。调用失败后保留请求摘要和配置上下文，允许重试或回到对应字段。

## 6. UI 视觉和交互规范

### 6.1 间距、尺寸和排版

统一使用 4 的倍数：`4 / 8 / 12 / 16 / 24 / 32`。页面级内边距 20，卡片间距 16，表单项间距 12，说明文字与控件间距 6—8。正文 14px，标题 16—18px，页面主标题 20—24px，辅助信息 12—13px，行高至少 1.45。

统一控件高度：紧凑表格操作 28—32px，普通按钮和输入 36px，重要提交按钮 40—44px。圆角采用 6（控件）、8（卡片）、12（大面板）三档，不再为单页引入随机圆角。

### 6.2 按钮状态矩阵

| 类型 | 默认 | Hover / Focus | Active | Disabled | 适用动作 |
|---|---|---|---|---|---|
| 主按钮 | 品牌色实心，白色文字 | 品牌色加深/轻微提亮，保留焦点环 | 更深品牌色或 1px 下沉 | 降低对比度但保留文字可读性 | 查询、保存、提交审批、发布 |
| 次按钮 | 白底、边框、正文色 | 浅品牌色背景、品牌边框 | 浅品牌色加深 | 灰底、禁止光标 | 重置、返回、取消、生成预览 |
| 链接按钮 | 语义色文字、透明底 | 同色浅底高亮 | 同色更深 | 禁止点击 | 表格行内查看、编辑、测试 |
| 危险按钮 | 危险色，仅用于不可逆或高风险动作 | 危险色加深并显示确认语义 | 更深危险色 | 降低对比度 | 删除、撤销令牌、下线 |
| 图标按钮 | 图标 + `aria-label` + `title` | 背景高亮 | 轻微缩放或颜色加深 | 低对比度 | 列设置、缩放、收起、复制 |

状态不能只通过颜色表达。发布、停用、删除、真实调用等动作应同时使用文字、图标或确认说明。所有自定义按钮和 Element Plus 按钮均需要 `:focus-visible` 焦点环；加载时保持按钮宽度、保留动作语义并防止重复提交。

### 6.3 表格规范

1. 第一优先级列：编码/名称、状态、最近更新时间或最近结果。
2. 第二优先级列：描述、脚本名、技术路径、来源详情；通过列设置显示，不在窄屏强行占位。
3. 操作列按“查看/进入 → 配置/测试 → 版本/文档 → 删除”排列；超过 3 个动作时收纳次要动作，避免一行出现五种同等重量的彩色链接。
4. 表头使用主题表头色，正文保持清晰对比；Hover 只改变行背景，选中行增加左侧 3px 品牌色标记，固定列必须覆盖滚动内容。
5. 状态同时显示文字和标签；启用、审批中、已发布、失败、未知不能只用绿/黄/红色块区分。
6. 空态说明“为什么为空”和“下一步是什么”，例如“尚无数据库来源，创建只读连接后才能配置数据库变量”。
7. 加载只显示内容区透明加载态；分页、筛选、列设置和横向滚动在 1280×720 下仍可访问。

### 6.4 设计器规范

设计器顶部始终显示：模型类型、规则编码、当前修订、保存状态、最后保存时间和唯一主动作。工具栏按“编辑 → 检查 → 保存 → 测试 → 发布”分组，撤销/重做/布局/缩放放入编辑工具组。节点选中、连线选中和属性面板使用统一的品牌色选中态；错误节点显示图标与可读提示，点击校验报告可回到节点。

节点语义需要直接可见：开始、条件、动作、聚合、结束；分支应显示命中策略、默认分支和未命中行为。工具栏按钮即使图标可理解，也保留中文短标签或悬浮提示，避免业务人员只能猜图标。

## 7. 响应式和可访问性验收

| 视口 | 验收重点 |
|---|---|
| 1920×1080 | 信息密度、表格不出现过度空白、设计器工具栏和画布平衡。 |
| 1440×900 | 详情页六步进度、主操作和首屏字段完整可见。 |
| 1280×720 | 关键字段和固定操作列不被遮挡；表单可提交、取消、看到错误。 |
| 768 | 侧栏紧凑、筛选工具栏换行、表格横向滚动、弹窗不超出视口。 |
| 560 | 表单单列、操作按钮换行、空态和错误可读。 |

键盘验收至少覆盖侧栏、页签、筛选、表格操作、对话框、设计器动作和校验定位。焦点环、`aria-label`、`aria-live` 状态和弹窗焦点回收要与鼠标操作具有同等信息量。

## 8. 推荐实施顺序

### 阶段一：流程连续性（P0/P1）

- 统一校验协议和问题定位字段。
- 在规则详情、设计器、变量、数据库、外数页面显示当前修订、草稿状态和唯一下一步。
- 完成创建后继续配置、失败保留输入、跨页返回恢复。
- 将测试证据绑定修订并显示过期状态。

验收：策略人员无需返回列表重新搜索即可完成“变量 → 规则 → 测试 → 送审”；每个阻断项都有一个可执行修复动作。

### 阶段二：复杂配置降负（P1）

- 数据库连接拆成连接信息、凭据/SSH、高级参数三段。
- SQL 参数绑定和结果预览与查询页复用。
- 外数预览、沙箱、真实调用分离。
- 规则测试、变量测试、模型测试和外数测试统一输入样例、状态、耗时和错误位置。

验收：参数错误、来源不可用、真实调用风险和返回结构问题都能在当前页面解释并恢复。

### 阶段三：密度、组件与性能（P2）

- 以业务任务为依据收敛 `theme-components.scss` 与 `element-override.scss` 的重复规则。
- 宽表操作收纳和列优先级统一，先覆盖变量、外数、数据库、模型、规则五类高频列表。
- 按能力拆分 `VariableList.vue`、`ApiDetail.vue`、`RuleDetail.vue`，父页面保留流程编排和数据提交。
- 设计器和看板进一步懒加载；以首屏 JS、交互延迟和回归测试验证收益。

验收：浅色/深色、主题切换、键盘焦点、1280×720 和 1920×1080 截图及 E2E 全部稳定；拆分前后提交负载和 ID 引用保持一致。

## 9. 不建议的做法

- 不把一级菜单改成分组菜单或隐藏入口来“简化”界面。
- 不把 SQL 改成只能选择字段的低代码表单。
- 不通过名称、编码或显示文本回溯变量和模型引用。
- 不用一个“绿色就绪”状态代替发布、测试、同步和实际执行证据。
- 不在未有任务基线时全局缩小表格或删除技术列。
- 不为每个页面单独创造一套按钮颜色、错误格式或保存语义。
- 不为了减少文件行数拆出只转发事件的组件，也不一次性重写大型单文件页面。

## 10. 现阶段完成定义

完成一次 UI/流程迭代时，应同时提交：

1. 代码、接口或状态协议变更；
2. 对应的组件/单元测试和有意义的失败场景；
3. `npm run dev` 页面启动检查、浏览器真实操作记录和截图；
4. `npm run lint`、`npm test`、必要时 `npm run build` 的结果；
5. 未覆盖的真实数据库、Redis、供应商、容量或权限场景说明。

业务验收建议记录五项指标：核心任务独立完成率、求助/返工次数、错误修复率、数据保真率、生效对象可解释率。没有这些基线前，不把“看起来更简洁”当作体验已经变好。
