## 1. 产品边界与完成定义

一级导航继续平铺。SQL 型业务人员继续直接编辑 SQL；图形化参数、说明和默认值是辅助能力。现有九种模型、变量与模型引用 ID、`ref_type`、用户编码原样保存、审批冻结及不可变制品链路继续保留。

“完成”同时要求功能实现、异常场景、对应自动测试和真实页面操作通过。涉及数据库、审批持久化、外数、发布或 SDK 同步的需求，还必须在对应真实依赖下验收。模拟 API 验证不能将这些需求直接标为交付完成。

本轮首批已实现项的代码与模拟页面验证完成；真实后端联调受本机 MySQL 不可用限制。后续未实现项是明确的交付计划，不代表已写入代码。

## 3. 首批已实现需求

### R01：工作台状态与异常恢复

业务人员打开项目或点击刷新时，需要知道信息是否已获取，而不是把空结果理解成已经配置完成。

状态展示依次识别：正在检查、状态读取失败、尚未获取检查结果、部分状态待确认、有待处理事项、当前检查项已就绪。加载期间不继续展示旧的下一步建议；失败后在原位置提供重新加载入口。刷新请求带递增序号，只有当前请求能写入结果、错误和加载状态。

验收已覆盖初次加载、空结果、完整结果、部分警告、失败重试和响应乱序。刷新失败清除旧数据，但不清除项目本身或任何配置内容。当前实现不持久化历史工作台快照。

### R02：执行检查识别失败与未知

“有记录”只能证明系统记录过执行。检查必须区分没有发布、没有近期记录、执行失败和无法取得完整状态。

| 条件 | 输出状态 | 下一步 |
|---|---|---|
| 无法读取发布数量 | UNAVAILABLE | 重新加载 |
| 尚无已发布规则 | BLOCKED | 先发布规则 |
| 无法读取近期执行数 | UNAVAILABLE | 重新加载 |
| 近 24 小时无执行 | ACTION_REQUIRED | 执行验证 |
| 最近一次执行失败 | ATTENTION | 排查执行失败 |
| 成功统计、最近记录或其结果缺失 | UNAVAILABLE | 重新加载 |
| 近 24 小时存在失败次数 | ATTENTION | 查看日志排查 |
| 现有证据未发现失败 | READY | 查看来源与修订详情 |

响应仍使用原有 `CheckItem`，没有数据库迁移。失败是技术执行失败，不等于业务“拒绝”；成功执行拒绝规则应仍是执行成功。当前项目聚合结果不承担 R05 的精确发布证明。

### R03：规则类型说明

用户在项目规则和规则管理两个入口选择类型时，均应看到用途、一个业务例子和创建后的操作顺序。两个入口复用同一组件，避免文案随页面分叉。

提示不改变选择、不自动创建字段、不改用户编码，也不替用户决定命中策略。当前验收通过选择决策流、QL 脚本、评分卡以及提交混合大小写编码，确认帮助信息变化而请求内容保持原样。九类类型仍完整可选。

## 4. 配置流程需求

### R04：基于实际依赖检查可用性

项目资源总数应继续作为资产概览，但不能作为规则是否可运行的唯一依据。检查以指定规则和修订引用到的 ID 为入口，沿现有依赖分析机制解析实际需要的变量、模型、规则、函数、外数、数据库或名单。

对每个依赖说明资源名称、作用范围、当前状态、是否已经生效、使用位置及修复入口。已绑定的全局资源应被识别；停用、删除、未批准、读取失败应分别表示。未引用的可选模型和外数不得成为阻断项。现有“所有项目字段数量”保留为指标，不能被偷换成“有效引用数量”。

验收至少包括：只使用全局字段的项目；只使用请求输入的规则；引用停用字段；没有模型的纯规则；规则引用错误 `ref_type`；外数只存在审批草稿；资源接口读取失败。旧数据无法追溯到 ID 时应提示待修复，不通过名称猜测关联。

### R06：校验报告可以直接修复

每条错误需回答“哪里有问题、为什么、怎样修复”。显示业务资源名称和字段标签；技术错误码、路径保留为辅助详情。校验服务可逐步补充结构化定位目标，例如资源类型、资源 ID、修订 ID、设计器节点/行的稳定标识及字段路径。

有定位目标时，点击跳转到对应资源或节点并显示相关错误；无定位能力时提供明确的操作建议。返回后可重新校验，保留正在编辑的草稿。只允许定位和提示，不自动修正变量 ID、转换业务名称或改变规则结果。

验收：失效变量、缺动作输出、树/流图结构错误、评分区间错误、模型输入不匹配均有可执行下一步；无权限时解释需要的权限；历史错误不能误跳到当前版本中无关节点。

### R07：动作权限与反馈

快捷操作复用当前菜单/路由能力判断，而不是新增另一套权限定义。具有查看权限但没有编辑权限的人仍能查看配置；涉及写入的入口应说明无编辑权限。无模块访问权限时不提供可执行跳转，或在业务需要的地方显示“需由具有相应权限的人员处理”。

服务端继续负责实际授权。前端隐藏按钮不能替代后端权限校验。验收覆盖仅项目查看、规则查看、规则编辑、审批与管理员角色，确认不会点击某个业务操作后无解释地回到看板。

### R08：数据库变量的可视化参数与返回值

保留 SQL 编辑器，复用现有查询页对占位符的识别能力。参数逐行配置“位置、类型、值来源、预览值”，值来源包括常量和稳定 ID 引用的业务字段；展示请求预览，使用户知道真正绑定了什么。JSON 模式继续保留，作为完整配置的表达方式，不作为普通路径的必经步骤。

执行预览后展示结果表及结构，用户可以选择需要的行/字段生成结果路径。明确返回单值、对象或列表的差异。零行、多行、字段缺失、类型不匹配、SQL 失败和超时分别提示，并展示当前异常策略将怎样影响变量值。

数据契约优先兼容现有 `sourceConfig`。表单与 JSON 必须双向一致，不能改变参数顺序、把 null 转成空字符串、把数值转成字符串或丢失字段 ID。SQL 内容保留用户输入，执行归一化只在明确的执行层处理。

验收：含引号/注释的占位符不误算；数值/布尔/null 正确保真；引用变量改名后 ID 关联仍有效；预览失败不会显示上一次成功结果；切换数据源后旧请求不能覆盖新结果；返回路径可解释；模拟和真实只读数据库分别验证。

### R09：依赖缺失时保留草稿并补齐

“没有可用来源”需区分没有创建、未审批、已停用、无权限以及加载失败。对应提供创建来源、查看审批、检查状态、联系有权限人员或重试入口。

跳转前保留当前字段草稿、项目 ID 和返回位置。外数或数据库审批未完成时提示等待生效，不能把草稿当作运行资源。返回后用户主动刷新可选来源，原字段名称、SQL、映射与参数均应仍在。禁止未经用户选择自动关联同名资源。

验收：半填表单跨页返回、审批未通过、创建失败、权限不足、目标删除及浏览器刷新等场景；不能形成“点击创建—返回清空”的循环。

### R11：SQL 校验语义一致

先检查后端当前只读 SQL 实现与支持的数据库方言，再决定统一词法分析或服务端校验契约。前端不应简单把字符串或注释中的分号视为第二条语句。

需求是正确识别单条只读查询，不是扩大权限。末尾终止符、普通注释、字符串字面量分别处理；多语句、锁定语句和写操作继续拒绝。CTE 等语法只有在后端和目标方言明确支持后开放。所有查询仍依赖只读数据库账号、参数化执行和行数限制。

验收用例同时在前后端运行：`SELECT 1`、允许的末尾分号、`SELECT ';'`、注释中含 `?` 或 `;`、两个 SELECT、锁定查询、写语句、嵌套查询及目标数据库的引用语法。不能通过删除用户 SQL 中的所有分号来“修复”。

### R13：创建后继续配置

在两个创建入口提供明确的“创建并继续配置”动作。创建成功后使用响应返回的规则 ID 进入现有详情或设计入口，并保留当前项目范围；不靠名称搜索新对象。需要保留“仅创建”路径时，两种动作有清晰语义。

提交期间防止重复创建；校验失败和网络失败保留输入，错误说明落在相关字段。创建成功但后续加载失败时允许重新打开已创建对象，避免用户再次提交产生重复规则。设计器的草稿/只读机制继续沿用。

## 5. 测试、发布与 UI 需求

### R10：测试证据属于确定的修订

复用现有样例、场景和批量执行能力，增加可选的业务预期断言及不可变执行记录。每次测试应记录规则 ID、修订 ID、依赖/制品摘要、输入快照、预期、实际、执行状态、断言状态、操作者和时间。技术执行成功与业务预期满足分别显示。

规则或依赖变化后，旧测试证据应标记“不适用于当前修订”，但仍能回看。不能把重新运行当前规则的结果覆盖到历史记录。审批详情展示本次修订的测试摘要和未覆盖提醒；策略是否强制指定测试集，应使用明确业务约束，不暗中改变全部项目的审批门槛。

验收覆盖边界值、缺字段、类型错误、未命中、命中多条、降级、嵌套规则、变更后证据过期、运行失败与业务拒绝。测试场景数量不能充当覆盖率；覆盖率需要有可解释的分母，如当前设计器可识别的分支集合。

### R05：可确认发布后的实际执行对象

发布详情应连贯展示待审批修订、批准制品、发布对象、部署绑定和最近实际执行记录。现有修订号与摘要继续作为依据。增加用于查询或展示的执行模式/环境信息前，应检查当前日志字段和兼容客户端上报方式。

精确验证需要匹配项目、规则、修订/制品和执行来源。对无法确认模式的历史日志，显示“未分类”，不能推定成生产调用。管理台测试、历史制品执行和新版本线上调用不能混为同一个“已经生效”。SDK 使用旧版本时显示同步状态与最近成功同步时间。

验收：发布 v2 后执行 v1；管理台测试成功但没有发布调用；SDK 暂时断连；回滚；同项目其他规则执行；下线后调用；历史日志缺新字段。所有情况都必须展示真实对象，不用一个绿色图标替代具体证据。

### R12：业务任务导向的 UI 一致性

为宽表定义最小必看列和次要列。编码/名称、状态、最近结果优先；脚本名称、长描述、技术 ID 等可按任务显示详情或列设置，不能直接删除用户需要的字段。主动作、普通操作、危险操作应可区分，但颜色不能是唯一信息。

关键表单增加字段释义、有效默认值说明和错误原因，数字配置明确单位、范围及实际效果。使用现有主题 token 和间距体系；浅色、深色、1280×720、1920×1080、浏览器缩放及键盘焦点均需验证。针对高密度页面，先验证任务是否完成，再决定是否改变密度。

设计器重点统一展示命中策略、默认分支、评分区间端点、终止作用范围和保存状态。已有追踪和条件编辑器继续复用，不能另建一套表达相同规则语义的独立前端模型。

验收：关键操作不被固定列遮挡；短屏可完成表单提交与取消；键盘可访问字段和错误；状态除颜色外有文字；错误后不必重新填表。业务人员需能准确说出当前规则对“未命中”和“多条命中”的处理。

## 6. 效率与工程需求

### R14：制品加载成本可度量后再优化

将端到端执行分解为鉴权、规则定位、制品读取、解码校验、依赖绑定、外数/模型、脚本执行、追踪和日志。小、中、大制品与嵌套规则分别测量冷/热路径。

如证据支持缓存已解码内容，缓存键至少考虑不可变摘要；部署绑定和项目上下文不得错误共享。冻结对象应不可变或每次执行安全隔离，不能把已写入参数的对象再次复用。缓存有容量上限、命中/淘汰指标，并测试篡改校验、回滚、绑定变更和多项目隔离。

验收要求前后结果相同、线程安全测试通过，且报告优化前后同样负载下的延迟、内存和 CPU。没有测量收益时允许仅交付基线，不强行加入缓存。

### R15：工作台统计查询可控且口径一致

先记录查询次数、返回体、行数和耗时，分别测试少量/大量规则与日志。优先精确字段投影、合并相同条件统计、合适索引与可解释的查询范围，再考虑短期缓存。

总次数、成功次数与最近记录可能在不同查询时刻发生变化，应避免出现不可能的成功率和误判。可以采用同一统计快照或显式采样时间与一致性状态；读取失败不能降为 0。缓存存在时页面显示刷新时间，手动刷新有可预期效果。

验收包含并发新增日志、部分查询失败、资源删除、大项目和空项目。服务端并发统计不能挤占核心执行连接池。

### R16：SDK 缓存与同步收敛

保留全量同步和原子快照替换。先测试缓存容量小于规则集合时的未命中和执行行为，再选择更合适的淘汰方案，不能直接把任意淘汰换成 LRU 就宣称问题已解决。

观察实际版本、期望版本、最近同步成功时间、失败次数、缓存压力以及日志丢弃计数。对断连期间通知丢失、乱序推送、全量同步失败、回滚和停用分别验证。若要增加重试或预热，必须避免重复计费、执行过期规则和服务重启风暴。

验收以最终正确版本和可解释状态为首要条件，收敛时间目标根据实际同步周期与业务容忍窗口确认。

### R17：按能力复用，逐步拆分配置页

优先随着 R08/R09/R12 抽取可复用参数表单、结果预览、草稿导航和校验反馈。父页面保持数据装配和流程编排，子组件只承担清晰的展示/编辑职责。序列化、校验与 API 提交尽量单点维护。

不得为了减少行数拆出大量只转发事件的组件。每次拆分保留前后相同的提交负载和可观察行为，以当前测试为回归依据。旧数据保存、版本回看、导入和主题样式均在检查范围内。

### R18：验收基线

| 指标 | 定义 | 如何采集 | 初步成功标准 |
|---|---|---|---|
| 独立配置完成率 | 完成指定任务人数 / 参与人数 | 代表性业务用户操作录屏与观察 | 先建立基线；可暂以首轮 5 人中至少 4 人独立完成核心任务为设计目标 |
| 返工与求助次数 | 每个任务重新填写、错误返回或求助的次数 | 逐任务记录 | 与基线比较下降，关键选择准确率不下降 |
| 错误可修复性 | 用户能定位并修正注入错误的比例 | 失效字段、无数据源、SQL 参数错误、类型错误 | 核心可恢复错误均有明确下一步；不要求复制错误码求助 |
| 数据保真 | 保存/载入/改名后 ID、名称、类型和值一致 | 契约测试、浏览器测试 | 全部必测案例通过，不容许“自动纠正”掩盖损坏 |
| 生效可解释性 | 用户能识别正在审批和实际执行的对象 | 审批、发布、回滚场景 | 能准确说出修订/制品及测试证据是否适用 |
| 端到端性能 | 吞吐、P50/P95/P99、错误率及资源使用 | 复用容量脚本，真实依赖与代表性负载 | 基线确认后制定 SLO；微基准不作为生产承诺 |
| 故障恢复 | 断连、超时、服务恢复后的版本与数据一致性 | 受控故障注入 | 无错误版本执行、静默丢数据或错误状态提示 |

上述目标是新需求的验收设计，不是已经取得的业务统计。参与人数有限时应保留原始任务记录，不将小样本结果推广为所有用户的结论。

## 7. 交付清单与实施注意事项

每个后续需求交付代码、状态/接口说明、有意义的回归测试、业务任务操作记录和未解决限制。前端完成开发服务页面验证后主动停止服务，再运行单元测试；涉及后端的变更完成全模块构建、实际启动和测试。浏览器必须从对应页面执行操作，不通过后端预造中间状态跳过业务步骤。

当前首批变更无需数据库迁移，不改变已发布制品。后续涉及日志字段、测试证据或结构化错误位置时，先设计向后兼容读取和迁移策略，禁止重放会清空现有数据的初始化快照。

本轮产物包括评估报告、本计划、验证证据、微基准程序、页面截图及代码变更。计划中的待实现项保留为可继续执行的工作包；真实环境受限项明确保留，不标为已完成。
