| 编译与执行 | `rule-engine-core`，每类独立编译器、QLExpress、变量上下文 | 将结构化模型转换为可执行规则 | 继续坚持 ID 引用和原样保留业务编码 |

## 4. 每日数百万进件的容量口径

日量不能直接换算成单机容量。平均 QPS = 日进件量 / 86400；下表峰值倍数为设计假设，并非用户真实流量测量。

| 日进件量 | 平均每秒进件 | 10 倍峰值假设 | 20 倍峰值假设 |
| --- | ---: | ---: | ---: |
| 100 万 | 11.57 | 115.74 | 231.48 |
| 300 万 | 34.72 | 347.22 | 694.44 |
| 500 万 | 57.87 | 578.70 | 1157.41 |

若每笔进件执行三条规则，规则执行次数还需乘 3；外数、数据库、模型、日志/账单也各自有调用或写入放大。以 579 笔/秒、平均耗时 500ms 为例，在途请求约 290；这只是稳定状态下的规划估算，不能用 P95 直接代替平均耗时，也不能据此设置 290 个线程。

当前开放执行 worker 默认按 CPU 数在 4—32 之间取值，等待队列 1000；来源解析配置默认并行度 4，队列随并行度增长，满时会由调用线程执行。这些上限有助于资源约束，但实际容量受规则复杂度、外数等待、模型内存、连接池与持久化速度共同影响。

按 500 万条/日、每条仅 2KB 原始日志估算，约 10GB/日、300GB/30 日，尚未计索引、复制、追踪、外数调用和账单。永久保留需要冷热存储预算与查询设计，不能只扩大单表和队列。

推荐场景矩阵：纯规则、数据库变量、多个外数、PMML、ONNX、带追踪、幂等命中/冲突、批量发布期间、依赖超时、节点退出；每类分别测冷/热缓存、单节点/多节点，记录成功决策吞吐、P95/P99、拒绝/等待/超时比例、队列最大值和恢复时间。

## 23. 计费日汇总后台任务、数据库聚合与恢复（2026-10-11）

N54的名单导出原来由 `selectList` 一次性加载全部记录，使用 `XSSFWorkbook` 生成完整工作簿，再由控制器写入 `ByteArrayOutputStream` 并复制成 `byte[]` 响应。三份对象会同时随名单规模增长，导出大名单时会把数据库结果、POI对象和响应缓冲叠加到 Java 堆；`autosizeColumn` 还需要扫描所有行。现改为控制器返回 `StreamingResponseBody`，服务按2000条一页读取并用 `SXSSFWorkbook(100)` 保留有限行窗口，固定八列宽度后直接写响应并释放临时文件。分页排序加入 `create_time,id` 双键，避免同一时间的记录在页边界重复或遗漏；接口仍是只读下载，不触发审批或改变有效记录。

N55的名单库、数据库、账单和分流实验项目选择原来在页面创建时分别请求500或1000条项目，超出首批的数据无法在下拉框中选择，编辑已有配置也可能因首批未包含项目而显示空值。新增公共 `ProjectResourceSelect`，复用已有远程筛选控件，按项目名称服务端分页搜索，选择后保留原始项目ID；当前编辑ID通过单独详情接口回填标签，响应乱序由选择器请求序号保护。页面保留项目切换时的现有规则/目标刷新逻辑。实验列表页和详情页的规则元数据也从一次1000条改为每页200条，按 `total` 或页长继续读取，正好整页时还会请求下一页确认结束；字段元数据仍按规则ID建立映射，没有通过编码回溯引用。验证包含第3页项目分页请求、第999个项目按ID回填、实验规则分页和名单/数据库/账单/分流相关定向测试。
