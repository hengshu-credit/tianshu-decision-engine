# 客户端规则预热缓存复核（2026-09-30）

## 发现

客户端全量同步把最新版规则和固定版本规则放进同一个 L1 缓存。原实现只按访问热度和同步返回顺序截断 `maxSize`；当固定版本排在前面、缓存刚启动尚无访问热度时，固定版本可能占满容量，按规则编码执行的最新版反而被丢弃。

## 修复

`L1MemoryCache.replaceSnapshot` 现在先保留非固定的最新版条目，再用剩余容量保留固定版本。最新版条目数量超过容量时仍按热度截断，这是容量不足时唯一可行的退化；固定版本不会挤掉默认最新版路径。缓存总量仍受 `maxSize` 限制，没有放大内存上限。

## 验证

- 新增回归：容量为 2、同步输入先放两个固定版本再放最新版时，最新版仍可按 `definitionId + null bindingId` 取得，缓存大小保持 2，至少一个固定版本仍可按绑定 ID 取得。
- `L1MemoryCacheTest` 10 项全部通过。

## 边界

固定版本的精确绑定和最新版跟随发布版本的语义仍由服务端同步接口及 Redis 发布事件决定；本修复只保证客户端预热和全量同步时的内存淘汰顺序。
