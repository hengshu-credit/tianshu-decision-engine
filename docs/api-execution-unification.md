# 外数配置与执行统一契约

本文件记录本次实现与验收范围。配置继续经审批生效，资源关联使用稳定 ID，旧配置保持可执行。

## 可视化配置中的字段目录

在「响应结构」导入最终响应样例，或在「多步链路」为每个请求、回调步骤导入自己的响应样例。独立样例用于生成字段目录，透传接口可以保持原有的响应映射不变。后续步骤从已完成步骤选择任务号，轮询条件选择当前步骤的状态字段，API 变量从最终结果选择业务字段。搜索支持完整字段目录，大响应可按整体绑定。

报文留存的解密、排除和超长字段配置均从对应报文字段目录选取。解密支持整个报文或具体字段；排除和超长字段策略还支持数组的具体下标及全部项。若处理脚本改变了结构，可导入处理后样例。搜索候选时保留原选择，使用“手动输入”可配置动态路径。

## 服务端执行排队

生产实验、服务端规则和开放规则通过鉴权和请求校验后，先向 MySQL 登记订单及原始请求。两台服务收到同一实验 `requestKey` 或配置了同一规则幂等键的请求时，共用同一追踪号。相同键搭配不同入参返回冲突。没有业务幂等键时每次提交独立接单，已取得追踪号的调用方可据此查单和恢复。

每副本的执行槽由 `RULE_EXECUTION_PARALLELISM` 指定，默认取 JVM 可见处理器数的四倍，至少 4 个。同步等待的默认容量为 256 笔、时限 90 秒，分别由 `RULE_EXECUTION_QUEUE_CAPACITY` 和 `RULE_EXECUTION_QUEUE_WAIT_MS` 控制，项目显式时限优先。等待容量、时限或项目并发额度耗尽时，已登记请求返回 HTTP 202 和追踪号，项目、接口的并发与速率限制继续生效。后台取得执行权后按原订单运行。凭据停用、版本冲突和业务执行错误会留在订单状态中。

调用 `GET /api/rule/runtime/executions/{traceId}` 查看 `QUEUED`、`RUNNING`、`WAITING_EXTERNAL`、可重试失败或成功状态，调用该路径的 `/result` 读取最终业务结果。实例宕机后，其他实例可在数据库租约到期后接手。外数异常修复后可向 `POST /api/rule/runtime/executions/{traceId}/resume` 提交空请求体，使用原始入参继续。默认复用原成功回执，已取得受理单号时只查询原单。直接规则、OpenAPI 规则和分流实验的生产或路由阶段进入等待后，后台在约 30 秒后尝试领取有原票据或回调登记的订单。多步链路在每个普通 HTTP 步骤发出前登记发送意图，获得该步回执后才推进。明确失败的后续收费步骤等待人工恢复，发送状态不明或原调用身份发生变化时保留原回执供核实。已声明的轮询仅继续原任务。调用方也可提前手动恢复。对于已发送但收不到回执、供应商也无法按业务单号查询的请求，需与供应商核实受理状态。显式选择 `externalRecoveryMode=CACHE_THEN_CALL` 才启用允许重新查询的恢复方式。新建空跑组的调用 API 外数开关默认关闭。

升级已有数据库时，在停应用并备份后执行 `2026-11-13-execution-queue.sql`。只有数据库已持久接单的请求才能由后台接管。如果客户端未取得追踪号，使用原业务幂等键和原请求重发可定位同一订单。已成功订单按配置的幂等保留期处理。

在分流实验的「冠军挑战 → 条件分流 → 分流条件异常」选择错误处理方式。选择「执行兜底组」时，条件求值、所需变量或独立路由规则报错会产生 `ROUTING_ERROR` 追踪，随后执行配置的兜底组。独立路由没有显式兜底组时使用冠军组。选择「暂停订单，修复后继续」时返回 HTTP 202 和实验追踪号，状态为 `PAUSED_ROUTING`，等待调用方按原追踪号恢复。采用最新版本且尚未选择生产策略的订单，可在修复条件并发布后继续使用原请求；指定固定版本或已绑定生产策略的订单继续校验原版本。已有实验和历史快照默认使用兜底，新建实验表单默认选择暂停。供应商已受理且等待原票据时继续按原票据处理。空跑组在生产分组确定后解析本组条件，调用 API 开关也适用于该组的条件取数。

### 异步接口的步骤结果

在「外数 API → 多步链路」为各步骤导入各自的响应样例，然后从本步的字段目录选择判断字段。HTTP 步骤在「本步骤成功、异常与重试判断」设置成功条件、异常条件和业务重试条件。未关联 API 的 HTTP 步骤独立评估本步条件，整条接口的成功条件在最终结果上评估。关联 API 的步骤先用关联接口配置，再采用本步骤提供的覆盖。

需要多次查询时启用「轮询此步骤」，设置完成条件、失败条件及命中失败时结束执行或继续查询原任务，同次响应命中两者时优先处理失败。回调步骤可用状态字段和值，或独立配置成功与失败条件树；使用成功条件树时无需另填状态路径。可选择收到失败通知后结束或继续等待下一条签名回调，首个终态回执生效。运行时按接口及步骤自身的配置判断，字段名与业务状态值由接入方维护。

## 调用身份

一次根规则执行（包含子规则）内，同一个 API 的同一组生效请求参数只执行一次完整链路，成功和失败均记忆；接口重试、轮询属于这条链路内部。显式允许覆盖的参数绑定到不同值时，形成不同调用。请求身份不能包含无关规则输出，也不能使用响应 TTL 缓存代替请求内去重。

## 配置职责

- API 管理：请求参数定义、可覆盖开关、必填与传空策略、鉴权、请求/响应条件分支、多步协议、重试、熔断、计费。
- API 异常条件：每个接口可配置异常条件树，支持路径缺失、存在、为空、非空、类型等于和类型变化等判断；命中后统一进入异常策略、重试和等待恢复链路。多步链路中的每个 HTTP 步骤还可配置独立的步骤异常条件树，内部规则数据源同样经过该判断，不会因协议不同而绕过条件。
- 变量与对象：按 API ID 选择来源，覆盖已开放入参，选择统一结果路径；对象子字段可独立选择原始响应路径。
- 统一结果：保留兼容的 body（组装结果），增加原始 response、request、authentication、steps、status 和调用元信息；字段取值不依赖日志采集开关。
- 预览只做解析与校验，禁止 HTTP、Token、回调注册及计费。真实测试进入正式调用链并展示追踪树。
- N 步链路以稳定步骤 ID 保存，请求/轮询/回调均在总截止时间内执行；后续步骤可引用前面全部步骤结果，禁止前向和循环引用。

## 结果与绑定示例

API 返回 `body`（组装结果）、`response`（原始状态码、响应头、响应体）、`request`（实际 URL、方法、Header、Query、JSON/Form）、`authentication`（本次鉴权调用列表）、`steps`（稳定步骤 ID 对应结果）、`status`、`callId`、`costTimeMs`。

变量通过 `apiConfigId` 关联 API，按 `resultPath` 取值。对象使用相同入口；`bindingMode=OBJECT` 整体绑定，`FIELDS` 逐字段取值。子字段 `sourcePath` 可以指定原始响应路径，例如 `response.body.data.mobile`。对象已有显式字段值优先，子字段的请求覆盖继承对象上其余覆盖项。

```json
{
  "apiConfigId": 42,
  "resultPath": "body.data.mobileStatus",
  "requestOverrides": {
    "phone-parameter-id": {
      "kind": "REFERENCE",
      "refType": "VARIABLE",
      "refId": 123
    }
  }
}
```

上例仅替换 API 明确开放的手机号参数。字段编码或显示名称变化时，按 `refId` 查找最新字段。覆盖后的值相同则共用结果，值不同则形成独立调用。对象字段的覆盖存于字段 `sourceConfig`。

规则可使用来源状态条件，或 `sourceStatusValue("VARIABLE", "字段ID", "HTTP_STATUS")` 读取状态。支持 `OUTCOME`、`HTTP_STATUS`、`BILLED`、`RETRY_COUNT`、`RETRIED`、`CIRCUIT_OPEN`、`EXCEPTION` 等维度。

## 多步与配置约定

- 可覆盖的链路入参在 API「请求字段」统一声明，各步骤从 `input.__apiFields.<参数ID>` 读取；步骤也可直接选择业务字段。前置结果通过 `steps.<步骤ID>.<结果路径>` 读取。
- 每个 HTTP 步骤可继承根 API 鉴权、关联另一个 API 的鉴权或自行配置鉴权。失败重试受次数、间隔、退避和非幂等重试开关约束。
- 步骤异常条件树以 `response.body`、`response.httpStatus`、`body` 等本步响应上下文判断；路径缺失与显式 `null` 保持可区分，类型判断支持 STRING、NUMBER、BOOLEAN、OBJECT、ARRAY、NULL 和 MISSING。保存与执行前均校验条件结构，避免空路径被当成“全部异常”。
- 不需要重试时选择 `FAIL_FAST`，将 `retryCount` 设为 `0`，并清空重试条件和 `retryBranches`；HTTP 状态码、连接错误和退避参数本身不会触发重试。选择 `RETRY` 时必须配置至少一次重试，或在多步链路的 `retryBranches` 中配置重试次数。
- 回调在提交前注册随机调用 ID，使用 HMAC-SHA256 校验；完成后清理注册。等待、轮询、鉴权和重试均受本次调用总超时约束。
- 条件按顺序选择第一个匹配分支，空条件作为兜底。响应样例保留字段原名，支持字段组装和整体取值。
- 表达式编辑器复用 Operand 结构，允许无外部副作用的内置计算函数；API 脚本不提供隐藏的网络下载入口。预览不注册回调、不获取 Token、不调用上游、不计费。
- JSON 支持显式 null；Query、Header 和表单的 null 按 HTTP 空字符串发送。默认省略空值，字段显式设置优先。
- 步骤追踪保存本步生效参数与前置步骤 ID，避免反复嵌入之前的追踪内容；大报文仍遵守原有诊断留存上限，完整运行结果独立于诊断留存。

## 大字段留存与配置存储

外数配置中的鉴权、Header、Query、请求/响应映射、统一执行链路、轮询、回调、计费、报文留存和测试样例由应用层校验 JSON，数据库优先使用原生 `JSON` 列，便于后续按路径查询；请求体模板、请求脚本和响应脚本等非结构化内容继续使用 `LONGTEXT`。应用启动同步会将历史配置列转换回 JSON，发现非法旧 JSON 时只告警并保留原列，避免静默丢失。

报文留存默认保存原文和全部字段。可在请求或响应侧按 JSONPath 添加“超长字段策略”：未配置或标记“保存”的路径继续保存，标记“省略”的路径始终从诊断副本移除，不根据本次实际内容长度临时改变意图；规则实际请求和响应不受该诊断策略影响。

### 大报文保存方式

在「外数管理 → API 接口 → 接口详情 → 业务配置 → 报文留存」分别设置请求与响应。旧接口保留原留存设置与原有失败回退行为；选用新保存方式并发布后，对之后的调用生效。

| 保存方式 | 实际写入的报文 |
|---|---|
| 仅原始报文 | 保存供应商发送或接收的原文。已配置的字段过滤和大小策略仍生效。 |
| 仅分析副本（可解码） | 保存选定来源的分析内容。来源可选原始内容或脚本处理结果。对 Base64 或 3DES 字段打开「留存解密副本」并选路径；失败时记录原因，原文字段保持空。 |
| 原始报文和分析副本 | 同时保存两种形式，便于分别查看签名原文与处理结果。 |

例如，仅保留响应中 `$.payload` 的 Base64 解码副本，可使用下列 `payloadCaptureConfig`。规则仍使用原有响应映射。

```json
{
  "request": { "storageMode": "ORIGINAL_ONLY" },
  "response": {
    "storageMode": "PROCESSED_ONLY", "source": "ORIGINAL",
    "decrypt": { "enabled": true, "mode": "BASE64", "path": "$.payload" }
  }
}
```

显式保存方式在每条调用日志中按所选类型留存正文，避免在通用 `response_body` 再序列化完整的响应信封及其所有嵌套步骤。调用 ID、阶段追踪、历史统计所需结果、实际赋值、账单、缓存与检查点有各自用途，仍按原契约保留。上游工作流与每个实际传输步骤均可产生审计记录；关联其他 API 的步骤采用所关联 API 的配置。离线重放只能使用已留存的业务字段与赋值证据。

## 异步等待、状态与恢复

异步提交获得的 `taskId`/`traceId`、轮询上下文和提交回执会写入规则幂等检查点。外数变量配置的异常策略支持 `SKIP`、`BREAK`、`WAIT`、`RETRY`；`WAIT` 将订单置为 `WAITING_EXTERNAL`，恢复时只查询原任务，不重复提交。V2 多步链路保存已完成步骤和当前等待步骤，恢复会跳过已提交步骤；回调注册在等待期间保留，终态后清理。

规则详情「执行配置 → 断点恢复外数」可对发布修订设置恢复方式。缺省的 `ORIGINAL_ONLY` 复用本订单相同接口、配置和生效入参的成功回执；已受理的异步任务按同一调用 ID 继续查询。明确失败且没有可用结果时允许重新请求。发送后未取得回执、供应商受理状态未知时保留未知状态，默认模式不会产生新的提交。`CACHE_THEN_CALL` 会在恢复时重新解析来源，外数先检查该接口配置的响应缓存，缺失或过期时允许新调用并计费。已经完成的订单仍返回终态结果。

实验执行和规则恢复入口均接受可选查询参数 `externalRecoveryMode=ORIGINAL_ONLY` 或 `externalRecoveryMode=CACHE_THEN_CALL`，仅用于本次重试，既有业务入参和请求摘要沿用原契约。生产实验按同一 `requestKey` 重发，或以实验 trace 调用恢复接口；组内规则 trace 也能恢复对应策略流。新接单的组订单会保存组类型、名单匹配时点及外数开关，按子追踪恢复时仍采用原设置。历史子订单缺少该上下文且需要继续执行时，接口返回原实验追踪号。新订单保存首次提交的原始请求，恢复可省略请求体；旧订单若保存的参数已被类型绑定转换，需提供原始入参。旧订单若没有留下任何供应商回执，不能从结果缺失推断供应商是否受理，请先对账。

`GET /api/rule/runtime/executions/{traceId}` 是状态与结果统一接口：未完成时返回 `status`、`attemptNo`、来源状态和脱敏步骤中间状态，完成时在同一对象的 `result` 中返回结果。`POST /api/rule/runtime/executions/{traceId}/resume` 可不带请求体（检查点已保存原始入参时），也可带原订单完整入参；服务端校验摘要后恢复原 revision 的规则。Java SDK 提供对应 `resumeExecution` 方法；直接接入方调用同一 Server API。

## 客户端缓存与高并发

L1 缓存达到上限时优先淘汰固定版本，最新版规则不会被固定版本增量推送挤出；如果缓存全是最新版，固定版本只使用本次回源对象而不继续占用槽位。冷启动或缓存淘汰后的同一 `ruleCode` 使用单飞加载，多个并发请求共享一次 HTTP 回源结果，失败后释放加载槽位允许后续重试。
