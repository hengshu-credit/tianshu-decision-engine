# 进件幂等、分流异常和外数步骤验收

2026 年 11 月 14 日，在独立双副本、MySQL 8.4、Redis 和本机模拟供应商上检查了实际接单、执行、追踪、到期恢复和名单工作线程。使用 60 万笔历史、120 万个坐标字段和 15 万条历史外数流水。规则和接口通过实际服务入口执行，所有供应商调用均来自可逐单对账的测试端。最终验收 JAR 的 SHA-256 为 `1967310731edb972f5f10351ab3d4a782784839ad2aea11526bd01f669e5a841`。

## 分流配置

控制台在「分流实验 → 冠军挑战 → 条件分流 → 分流条件异常」提供两个选项。旧实验和旧版本快照按兜底处理，新建表单默认暂停。独立路由成功但没有匹配组时，按原实验配置选择兜底或冠军组。

| 场景 | 配置与实测 |
| --- | --- |
| 分组条件执行报错 | 修复前返回成功的冠军组结果。配置 `FALLBACK` 后执行兜底组，追踪同时留下条件错误和所选分组。配置 `PAUSE` 后返回 202、原实验追踪号及 `PAUSED_ROUTING`，未执行策略。修复条件后在另一副本恢复，同一追踪号第 2 次尝试命中修复后的组。 |
| 独立路由规则的依赖明确失败 | 实测相同故障分别执行兜底组或暂停。暂停后修复供应商再恢复原订单，只有失败接口被重试。供应商已受理、结果仍在等待时保留原单查询，避免提前发放额度。 |
| 固定版本与重新发布 | 最新版配置只允许尚未绑定生产组的路由暂停单在恢复时采用修复后的配置。已绑定的生产、测试分组继续校验规则身份和修订，固定版本继续使用指定快照。成功订单重复提交返回原终态。 |
| 测试组开关 | 修复前，测试组条件可能提前访问已关闭的 API。实测关闭后供应商 0 次，开启后原提交 1 次，按条件命中相应组。空跑条件或规则运行异常保留在测试结果。已接收订单遇测试组线程队列满时使用当前执行槽处理。 |

## 异步接口与数据源

「外数管理 → API 接口 → 多步链路」的每个 HTTP 步骤可设置自己的成功、异常及业务重试条件。轮询的完成条件、失败条件、失败后终止或继续，和回调的成功条件树、失败条件树及失败处理方式都由配置决定。最终接口的成功条件评估最终结果。响应字段可以通过各步自己的样例和字段目录选择。

- 实测将受理判定改为不匹配的供应商值，受理发生 1 次、后续轮询 0 次。正常配置得到额度 60,000、年利率 960 基点和期限 24 个月。改变轮询完成条件后仅查询一次，后续策略按返回的实际数据拒绝。浏览器中导入并修改步骤条件、保存、重新打开、提交和审批，随后使用已发布配置调用真实 HTTP 入口成功。
- 在第二个普通 HTTP 步骤被供应商接收后丢弃响应。修复前默认恢复导致该收费步骤实际提交两次；修复后供应商计数为 1 并保留待核实状态。改为明确返回 503 后，修复供应商并手工恢复只重试失败步骤，先前已受理的提交仍是 1 次。
- 已取得票据后切换外数配置，修复前会形成第二个异步任务。默认恢复现在校验同一消费来源的调用身份，恢复原配置后按原票据得到结果，始终只有 1 次提交。显式选择 `CACHE_THEN_CALL` 时，缓存未命中可以再发起查询；跨副本缓存命中时复用成功结果。另以两笔独立规则订单实际核对 Redis 缓存和账单，同一查询供应商 1 次、账单 1 条，金额 0.123456。
- 已受理的直接规则及独立路由规则先返回 202，随后只查结果即可完成。签名回调在第一次响应 40 秒后由另一副本接收；配置成功树时未提供状态路径，失败通知配置为继续等待，再发送两份不同的终态通知，最终采用第一份成功回执。回调登记按恢复窗口保留，原订单不会重新提交。
- 恢复期间结果查询连接中断，已取得的受理回执保留；在自动恢复时还会重新校验原始回执。无法确认的普通收费步骤需要业务核实，确认后的显式重新查询可能产生新费用。

## 并发、动作与恢复

| 演练 | 证据 |
| --- | --- |
| 同单并发 | 64 个不同业务键，每个键在两个副本同时发送 4 份，共 256 次提交，最多同时在途 64 份。每键一个实验订单、一份最终正确结果及一条成功生产组记录。32 笔通过、32 笔拒绝。全部 64 个键更改入参重发均被拒绝。供应商流水有 672 次同步取数、16 个异步任务，符合各业务路径。 |
| 双副本强停 | 在供应商给出原任务号、步骤回执已经落库后对两个应用同时发送 SIGKILL。11 单排队、8 单执行中，启动就绪后 112.4 秒内 19 单全部完成。客户端只查询，异步任务提交 1 次，18 个名单任务逐个核对四种值。 |
| 失败后写名单 | 实测同一失败订单重试，`writeOnFailure=false` 时无名单回执，开启后仅 1 张回执、4 条记录，记录来源为 FAILED。根流程正常返回业务拒绝按成功完成的规则处理。 |
| 测试组子追踪恢复 | 主策略成功且测试组等待时，按子追踪跨副本恢复。默认禁止写入时名单记录为 0；显式开启测试组写入时仅 1 个任务、4 条记录，记录标明 TEST 和原实验 ID。两种情况下，测试组均未写入线上进件历史。 |
| 日志与名单接管 | 回归用例在原实例持有目录锁时验证其他副本不消费；释放锁后，持续运行的副本接管旧目录并使用原身份投递。验证了账单和名单事务回执去重及名单的原有效期。 |

## 适用边界

实验顶层 `requestKey` 和规则端已发布的幂等键决定能否识别重复提交；只配置用于分桶的请求键表达式不足以识别两次未带幂等键的独立 HTTP 提交。结论适用于保留期内且服务端已持久接单的逻辑订单。不同订单同时发生的跨副本冷缓存缺失仍可能分别访问供应商；跨订单使用 Redis 缓存不能作为供应商受理凭证。共享日志卷和 MySQL 回执需要在实际部署中保留。真实供应商及跨机房存储灾备未参加本次演练。
