# 服务端组件资源上限与吞吐量

在同一台 Docker Desktop 主机上，将同一份已关闭的 MySQL 数据卷快照分别恢复到每种资源配置，再从 Nginx 向两个服务端副本发送真实分流实验请求。吞吐量按最终业务结果校验通过的订单数除以整组墙钟时间计算。HTTP 202 只表示接单，等待最终结果的时间也计入。

## 测量口径

- 使用提交 `ddd9cd5324a8` 的同一服务端 JAR，SHA-256 为 `57f15dd72e9e4336cd7637e59f5c6aba06732efdf134ca23248809f28115b534`。每组均从 600,000 笔合成历史、1,200,000 个索引坐标值、150,000 条历史 API 流水和两笔无坐标历史开始。每个副本预热两笔完整策略。所有分组使用同一台 32 逻辑核、Docker 可见约 15.5 GiB 的本机测试环境。
- 完整策略评估约 50 项规则，包含 14 个同步 API、1 个 8,000 字段的异步报告、10 次数据库查询、5 次名单匹配、SFTP、3 次模型计算，以及 1 公里范围内的当日、7 天、30 天统计。同步供应商模拟约 35 ms 延迟，使用原任务号轮询异步报告。完整追踪、双副本、缓存设置、数据库持久性、供应商接口限额及请求内容保持一致。
- 持续组并发 32、共 96 单，完成一笔即补一笔。突发组同时发 64 单。另在原上限和联合扩容下复测混合业务，每秒 0.24 单背景流量，在第 40 秒叠加 48 单。联合组再发一个 128 单突发。每轮分别统计通过、拒绝、实际额度、年利率、期限、追踪、GPS、名单写入及外部供应商收到的每笔请求。
- 表中 CPU 单位为核，内存单位为 MiB，应用一栏按每副本计。基线 JVM 堆上限 768 MiB、InnoDB 缓冲池 384 MiB，与上一轮容量夹具一致。扩应用时堆调到 1,536 MiB，扩 MySQL 时缓冲池调到 1,536 MiB。纯 CPU 组保留原内存、堆和缓冲池。纯内存组保留原 CPU。仓库小资源部署原有的 MySQL 缓冲池示例为 1 GiB，生产环境应核对实际设置。
- 使用每个容器的 cgroup 核验生效的 CPU 和内存上限，查询 MySQL 核验实际缓冲池。JVM 与引擎继续按可见 CPU 自行计算默认执行槽。外数接口响应缓存 TTL 为零。本轮 Kafka 未参与 HTTP 执行链路，没有 Kafka 吞吐测量。

## 正确性和资源观测

正式测量共 2,704 单，2,668 单通过、36 单拒绝。首次返回正确业务结果 2,539 单，另有 165 单先返回 202 后只轮询最终结果，客户端重提 0 次。逐单匹配实验记录、策略根追踪和供应商流水，共 37,604 次同步取数、2,578 次原异步提交及 5,156 次原任务结果查询。36 笔拒绝均核对手机号、身份证明文及 MD5 名单记录。各阶段结束后校验了持久化发件箱和审计队列的排空结果。各配置的 MySQL 死锁计数增量合计 0。

- 原上限，首轮的 MySQL 平均占用 0.299 核，受限调度周期为 38.0%。两个应用副本合计 0.597 核，受限调度周期分别为 41.1% 和 42.1%。
- 只扩两个应用副本的 MySQL 平均占用 0.348 核，受限调度周期为 61.5%。两个应用副本合计 0.892 核，受限调度周期分别为 0.8% 和 0.9%。
- 只扩 MySQL的 MySQL 平均占用 0.355 核，受限调度周期为 0.1%。两个应用副本合计 0.610 核，受限调度周期分别为 47.4% 和 48.2%。
- 只扩四类组件的 CPU的 MySQL 平均占用 0.446 核，受限调度周期为 0.8%。两个应用副本合计 0.943 核，受限调度周期分别为 0.6% 和 0.9%。
- 四类组件一起扩容的 MySQL 平均占用 0.553 核，受限调度周期为 0.8%。两个应用副本合计 1.054 核，受限调度周期分别为 3.2% 和 1.9%。

## 扩容次序

单独扩大内存、堆及缓冲池时，持续吞吐为 0.783 单/秒，原上限两次测量为 0.781 和 0.836。只扩应用及 MySQL 的 CPU，同时沿用原来四类组件的内存、堆、缓冲池、Redis 和 Nginx 的 CPU 时，持续吞吐为 1.217，64 单突发为 1.103。

Redis 单独扩容后的持续吞吐为 0.787，Nginx 单独扩容为 0.782。本工作负载应结合基线复测的波动判断这些差异。2 核方案下两个应用副本合计最多使用 4 核，实际消耗见上面的 cgroup 数据。所有数值来自完整业务路径，增加配额后的吞吐提升不会与配额倍数成正比。

应用元数据库与模拟只读账务库共用测试 MySQL；分库部署时各数据库的扩容收益要分开测量。CPU 占用是整组平均值。上限是资源额度，调度周期受限比例按 cgroup 的 `nr_throttled / nr_periods` 差值计算。复测使用可控供应商和本机磁盘，单轮 96 笔持续补单不能代表数小时稳定容量，真实供应商延迟、收费限制和数据库存储性能都会改变绝对吞吐。新增部署参数及生效步骤见[部署手册](../deployment.md#服务端容器配额)。
