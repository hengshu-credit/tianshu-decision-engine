# 天枢决策引擎产品与工程优化审计（2026-09）

## 1. 审计范围与方法

本次审计独立于仓库中已有规划，按实际代码、控制器、测试、页面模板和执行链路重新梳理：

- 前端：`rule-engine-builder-ui/src/views`、路由、布局、API 封装、单元测试；
- 后端：`rule-engine-server` 管理控制器、规则编译/执行、变量来源解析、数据库连接池、日志与计费；
- 核心：`rule-engine-core` 的 QLExpress 预编译缓存和执行上下文；
- 操作验证：前端单元测试、Vite 构建、ESLint、数据库连接池回归测试、Vite 页面启动检查。

当前基线：

- 前端 `npm test`：197 个测试文件、2399 个测试通过；
- 前端 `npm run build`：通过；存在既有的大 chunk 警告（`GraphDesignerNavigator`、看板等）；
- 前端 `npm run lint`：通过；
- 后端 `DBConnectPoolsTest`：9 个测试通过；
- 根目录 `mvn test`：现有 `rule-engine-client-http` 的 6 个 loopback 测试因本机无法建立回环监听失败，`rule-engine-core` 与 `rule-engine-server` 相关测试可运行；该问题属于环境/测试启动条件，需单独治理。

## 2. 已具备的产品能力

平台已经不是“规则编辑器样例”，而是具备完整治理骨架的决策平台：

1. 九类规则设计器、变量/数据对象/常量、名单、外数、数据库、模型、函数；
2. 草稿、评审、批准、发布、下线、版本比较、回滚和不可变决策制品；
3. 规则测试、固定用例、表达式追踪、执行日志、外部调用日志、账单和实验；
4. 稳定 ID 引用、`ref_type` 类型区分、发布制品冻结依赖；
5. 开放接口、Java SDK、HTTP-only SDK、Redis 规则推送；
6. SQL 仍然可直接配置，一级菜单仍保持平铺。

这些能力应作为后续优化的基础，不应重复建设同名模块。

## 3. 主要问题与证据

### P0：数据库校验 SQL 可执行写操作（已修复）

`DBConnectPools.testConnection` 原来直接执行 `validationQuery`，没有使用查询接口的只读 SQL 检查。一个误配置的 `UPDATE`、`DELETE` 或带锁查询可能在“测试连接”时产生写影响。

本次修复：

- 在创建测试连接池前复用只读 SQL 词法检查；
- 只允许单条 `SELECT`，去除合法结尾分号；
- 增加回归测试，确保写语句在打开连接前被拒绝；
- 配置页说明校验 SQL 规则。

### P1：规则配置路径长，缺少业务结果导向的进度模型

当前常见路径是：

`新建规则 → 进入详情 → 创建/选择生命周期修订 → 输入字段 → 输出字段 → 进入九类设计器 → 保存/编译 → 规则测试 → 提交审批 → 批准 → 发布`

问题：

- 详情页虽然有生命周期、输入、输出、开放接口等 Tab，但用户需要自行判断下一步；
- “保存内容版本”“生命周期修订”“当前发布版本”是正确的治理概念，却没有统一显示“还差什么才能测试/提交/发布”；
- 设计器的动作按钮各自实现，首次使用者无法区分暂存、编译、测试、提交和发布的边界；
- 规则测试页同时承载范围选择、字段生成、手工参数、固定用例、批量执行、追踪树，认知负担高。

证据：`RuleDetail.vue`、九个 `designer/*.vue`、`RuleTest.vue` 均为大型单文件组件，职责和交互状态高度集中。

### P1：数据库配置页把“入门配置”和“运维调优”混在一起（已部分修复）

原页面同时展示作用范围、JDBC URL、主机端口、SSH、账号、连接池、校验 SQL、状态等字段。新用户需要在“自动生成 JDBC URL”和“手填 JDBC URL”之间做选择，还要理解连接池参数。

本次已增加：

- 配置步骤提示；
- 高级连接池与校验 SQL 折叠；
- 测试连接的加载态、成功/失败状态和可读错误；
- 保留 JDBC/SQL 直接配置能力。

仍需继续：

- 基础连接方式与 SSH 隧道分成明确步骤；
- 采用“连接信息 → 凭据 → 高级”分段校验；
- 通过数据库类型提供可复制的安全默认值和字段级错误；
- 测试连接返回驱动、网络、认证、校验 SQL 四类结果，而不是只返回一段字符串。

### P1：变量页和外数页承担过多职责

`VariableList.vue`、`ApiDetail.vue`、`RuleDetail.vue` 的代码体积明显大于其他页面。变量页同时管理普通变量、对象字段、常量、字段校验、API/数据库/名单来源、在线取数测试和审批；外数页同时管理数据源、鉴权、请求参数、响应映射、缓存、重试、异步轮询和脚本。

风险：

- 修改一处状态容易影响其他 Tab；
- 业务人员无法判断“配置来源”“测试样例”“发布后生效”之间的关系；
- 错误提示常停留在 toast，无法定位到字段或下一步；
- 页面加载和保存操作缺少统一的脏数据/离开保护。

### P1：生命周期与设计器之间缺少统一的“可操作校验报告”

后端已有 preflight、依赖校验、环检测和制品摘要，但不同入口的反馈形态不同：

- 设计器有自己的状态条和问题定位；
- 详情页有生命周期面板和校验报告；
- 规则测试失败主要靠错误字符串；
- 外部资源测试和变量取数测试也各自维护状态。

结果是“同一个问题在不同页面有不同说法”，业务人员很难判断是输入缺失、引用失效、依赖不可用还是执行超时。

### P1：执行链路总体设计合理，但根日志和计费仍在请求线程同步落库

已经具备：

- QLExpress 预编译脚本有 1024 项有界缓存；
- 来源解析支持可配置并行度、队列和 deadline；
- 外部调用有连接池、token/响应缓存、single-flight、熔断与异步明细日志；
- 开放规则执行有有界线程池、超时和队列满保护；
- 模型执行有独立超时线程池。

仍存在的性能风险：

- `RuleExecuteService` 每次执行后同步保存根执行日志；
- 计费记录在请求线程同步查询配置并插入；
- 根日志含输入、输出和完整追踪 JSON 时，数据库写入和序列化会放大 P95；
- 当前 `application.yml` 将来源解析并行度配置为 4，但代码在未配置属性时回退为 1，部署环境容易出现吞吐差异；
- 追踪开关虽然存在，测试和日志页面容易让用户默认开启大体积 trace。

启动实测还发现：数据库中的 2 个已发布版本在 QLExpress 预热时被拒绝，但应用仍然进入 `Started` 状态。当前日志能看到错误，却没有把规则可用性暴露为 readiness 或管理台阻塞状态，容易出现“服务健康但部分规则不可执行”。

### P2：SQL 能力可用，但高级用户体验仍不完整

当前只读词法检查防止多语句、写入和锁定查询，参数占位符也有前后端共用测试语料。仍需补齐：

- 对 `WITH` CTE、数据库方言函数和安全误报给出明确提示；
- SQL 参数从“第 N 个 ?”提升为带来源字段、类型和样例的绑定向导；
- 查询预览、变量配置、字段映射三者复用同一份 SQL 分析结果；
- 保存前提供“返回行数、结果路径、类型推断”的可视化预览。

### P2：可观测性指标不够面向运维决策

现有日志和看板能力丰富，但还缺：

- 执行队列拒绝数、来源解析队列等待时间、缓存命中率、日志丢弃数；
- 按规则版本/制品摘要的 P50/P95/P99；
- 外数重试、熔断、陈旧缓存和数据库连接池耗尽的统一告警；
- 规则发布前的“性能预算”检查。

### P2：前端资源体积和页面拆分仍有优化空间

构建已通过，但有大 chunk 警告，设计器导航和看板依赖集中在大包中。大型单文件组件还会增加首屏后的解析与热更新成本。需要在不破坏页面路由的前提下做组件级拆分和更细粒度懒加载。

## 4. 业务人员使用复杂度结论

### 当前适合的人群

- 能理解变量编码、数据类型和基础规则逻辑的风控/策略人员；
- 能编写或审核 SQL 的数据/策略人员；
- 有研发协作的模型和外数接入人员。

### 当前不适合直接独立完成的人群

- 只熟悉业务政策、但不熟悉 ID 引用、脚本名、JDBC 或响应路径的人员；
- 需要一次性配置“数据源 + 变量 + 规则 + 测试 + 审批”的新项目成员；
- 需要快速定位“为什么不能发布”的审批人员。

目标不应是删除高级能力，而是给同一能力增加分层入口、默认值、术语解释、可执行的下一步和统一校验结果。

## 5. 新的功能优化与完善计划

| 阶段 | 目标 | 需求与验收 |
|---|---|---|
| P0（已完成） | 防止数据库测试写操作 | 校验 SQL 与在线查询共用只读检查；写/锁/多语句在连接打开前拒绝；有回归测试。 |
| P0（下一步） | 统一配置校验协议 | 所有资源测试/规则 preflight 返回 `code、severity、path、title、message、nextAction`；页面可直接定位字段或设计器节点。 |
| P0（下一步） | 发布前最小闭环 | 规则必须显示输入、输出、模型内容、编译、测试样例、审批、发布六项状态；缺项只给一个主下一步；已发布版本预热失败必须进入 readiness/管理台阻塞状态。 |
| P1 | 规则“业务流程向导” | 保持一级菜单平铺，在规则详情和设计器顶部增加可收起的 1-6 步进度条；每步可跳转、显示阻塞原因和完成证据。 |
| P1 | 数据源分层配置 | 基础连接、凭据/SSH、高级池参数三段式；按数据库类型提供安全默认值；测试结果分网络/认证/SQL。 |
| P1 | 变量来源向导 | 普通输入、计算、API、数据库、名单、衍生来源使用统一卡片；先选来源再显示专属字段；SQL 参数自动绑定上游字段。 |
| P1 | 统一测试工作台 | 规则测试、变量取数测试、模型测试、外数测试使用相同的输入样例、执行状态、耗时、错误路径、trace 开关和收藏用例结构。 |
| P1 | 审批与发布可解释性 | 审批详情展示变更前后字段、影响资源、依赖差异、性能预算和回滚点；批准后明确“何时线上生效”。 |
| P2 | 执行性能治理 | 根日志和计费改为有界异步批量写入；提供队列深度、丢弃计数、写入延迟；按请求类型保留最小必要 trace。 |
| P2 | 来源解析与缓存治理 | 提供并行度、超时、缓存 TTL、single-flight、熔断状态的项目级默认值和运行指标；发布前检查依赖数量与预算。 |
| P2 | SQL 智能配置 | 支持安全 CTE 白名单/方言策略、参数类型推断、结果路径预览、字段类型冲突提示；保留直接 SQL 编辑。 |
| P2 | 组件与包拆分 | 将变量、外数、规则详情拆分为业务卡片/子组件；设计器导航和看板进一步懒加载；验收以首屏 JS、交互延迟和回归测试为准。 |
| P3 | 版本与实验联动 | 规则/模型/函数/实验统一查看“当前线上制品、草稿、实验组、回滚目标”；实验切换前自动做依赖和性能检查。 |
| P3 | 运营与容量演练 | 提供压测脚本、数据库/Redis 连接池容量基线、备份恢复演练、日志保留策略和告警 runbook；用真实部署环境完成浏览器 E2E。 |

## 6. 建议的迭代顺序

1. 先完成统一校验协议和规则六项进度，这会直接减少业务人员的试错；
2. 再完成数据源、变量、测试工作台的分层配置，降低首次配置复杂度；
3. 并行推进根日志/计费异步化和性能指标，避免配置体验优化后被线上延迟抵消；
4. 最后做大型组件拆分、SQL 智能化和实验/版本联动。

## 7. 不应改变的产品边界

- 一级菜单继续平铺；
- 直接 SQL 配置继续保留；
- 变量、模型、规则引用继续只用稳定 ID；
- `ref_type` 继续显式区分变量和模型；
- 导入字段名、编码和用户输入原样保留；
- 发布制品继续冻结依赖，不能回溯读取线上实时元数据。
